A component is data: a manifest and a set of templates under
[`components/`](https://github.com/Tales-of-zuna/gobento/tree/main/components).
Adding one never requires a change to gobento's engine. Before you read this
page, skim [Slots and contracts](/docs/concepts/slots-and-contracts) and
[Traits](/docs/concepts/traits).

<Callout type="info" title="Start with a proposal">
  A new component adds options to `gobento new`, so it is a behavior change. Open a [component
  request](https://github.com/Tales-of-zuna/gobento/issues/new?template=component_request.yml) to
  discuss it, then follow the OpenSpec workflow in
  [CONTRIBUTING.md](https://github.com/Tales-of-zuna/gobento/blob/main/CONTRIBUTING.md).
</Callout>

gobento builds a project from four components, one of each required kind,
and at most one frontend, which is optional:

| Kind           | Fills                                                 | Example   |
| -------------- | ----------------------------------------------------- | --------- |
| `architecture` | the entry point, the shared types, and the layout     | `mvc`     |
| `framework`    | the HTTP handlers                                     | `nethttp` |
| `database`     | the database connection and schema                    | `sqlite`  |
| `data`         | the data access that implements the shared interfaces | `sqlc`    |
| `frontend`     | the web pages, served next to the API (optional)      | `htmx`    |

There is no template per combination. An architecture declares _slots_, each
of the other components fills a slot, and _traits_ say which components fit
together.

## Directory layout

Each component lives in `components/<kind>/<name>/`. The directory holds data
only:

<Files>
  <Folder name="components" defaultOpen>
    <File name="versions.yaml" />
    <File name="embed.go" />
    <Folder name="<kind>" defaultOpen>
      <Folder name="<name>" defaultOpen>
        <File name="component.yaml" />
        <File name="notes.md.tmpl" />
        <Folder name="files" defaultOpen>
          <Folder name="<slot>" defaultOpen>
            <File name="<file>.tmpl" />
          </Folder>
          <Folder name="root" defaultOpen>
            <File name="<file>.tmpl" />
          </Folder>
        </Folder>
      </Folder>
    </Folder>
  </Folder>
</Files>

| Path                       | Purpose                                                                                                              |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `versions.yaml`            | The [version rules](#versions) for every generated project.                                                          |
| `embed.go`                 | Embeds the catalog into the gobento binary. The only Go file under `components/`.                                    |
| `component.yaml`           | The [manifest](#the-manifest). The loader validates it.                                                              |
| `files/<slot>/<file>.tmpl` | Rendered into that slot's directory, for example `files/store/` for the store slot.                                  |
| `files/root/<file>.tmpl`   | Rendered into the project root, for example `sqlc.yaml`. Root paths are checked for conflicts with other components. |
| `notes.md.tmpl`            | Optional notes appended to the generated README.                                                                     |

For example, `components/framework/nethttp/files/handlers/router.go.tmpl`
becomes `internal/controllers/router.go`, because `mvc` puts the `handlers`
slot in `internal/controllers`, `internal/items/itemshttp/router.go` with
`vertical-slice`, and `internal/adapters/httpapi/router.go` with `ddd`.

### The `.tmpl` rule

Every file under `components/` must end in `.tmpl`, except `component.yaml`,
`versions.yaml`, and `embed.go`. The suffix is removed in the output. As a
result, no template is ever compiled, vetted, or linted as part of gobento
itself.

### Dotfiles

No file or directory name under `components/` starts with `.`. Write `dot-`
instead: a leading `dot-` in any path element becomes `.`, so
`files/root/dot-gitignore.tmpl` renders as `.gitignore` and
`files/root/dot-github/workflows/ci.yml.tmpl` renders as
`.github/workflows/ci.yml`.

Templates are read with `\r\n` normalized to `\n`, and the repository's
`.gitattributes` forces LF line endings anyway.

The catalog loader enforces these rules, and its tests load the shipped
catalog, so a mistake fails `make test`.

## The manifest

`component.yaml` has exactly these keys. Unknown keys are rejected, so a typo
fails loading instead of being ignored.

| Key           | Kinds             | Meaning                                                                                           |
| ------------- | ----------------- | ------------------------------------------------------------------------------------------------- |
| `name`        | all               | Must equal the directory name and match `^[a-z][a-z0-9-]*$`. A frontend may not be called `none`. |
| `title`       | all               | Required. A short display name, such as `SQLite`.                                                 |
| `description` | all               | Optional. One sentence, shown in the [Components reference](/docs/components).                    |
| `slots`       | architecture only | The slots the architecture declares (at least one).                                               |
| `provides`    | all               | Traits this component provides: trait → value.                                                    |
| `requires`    | all               | Traits this component needs: trait → list of accepted values.                                     |

Each slot has these keys:

| Key         | Meaning                                                                                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `dir`       | Required. The slot's directory, relative to the project root. It is a template over `.Project`, for example `cmd/{{.Project.Name}}`.                                              |
| `package`   | Optional. The Go package name. It defaults to the last element of the rendered `dir`; set it when that is not a valid package name, as the entry point does with `package: main`. |
| `filled_by` | Required. The kind that fills the slot: `architecture`, `framework`, `database`, `data`, or `frontend`.                                                                           |
| `required`  | Optional, default `false`. The selection must fill the slot. A slot of an optional kind, such as `web`, is not required.                                                          |

Slot names match `^[a-z][a-z0-9_]*$`, because templates use them as field
names (`.Slots.handlers`), and `root` is reserved.

This is a complete architecture manifest. gobento's documentation test loads
it with the catalog loader, so it stays correct:

{/* example-manifest */}

```yaml title="components/architecture/mvc/component.yaml"
name: mvc
title: Model-View-Controller
description: Models, controllers, and a data store in separate packages, wired together in cmd/<name>.
slots:
  entry: { dir: 'cmd/{{.Project.Name}}', package: main, filled_by: architecture }
  models: { dir: internal/models, filled_by: architecture }
  handlers: { dir: internal/controllers, filled_by: framework, required: true }
  database: { dir: internal/database, filled_by: database, required: true }
  store: { dir: internal/store, filled_by: data, required: true }
  web: { dir: internal/views, filled_by: frontend }
```

A component does not list the slots it fills. They follow from its layout: a
template under `files/<slot>/` fills `<slot>`.

The manifests of other kinds declare the traits they provide or require. This
is `sqlite`'s:

```yaml title="components/database/sqlite/component.yaml"
name: sqlite
title: SQLite
description: SQLite through modernc.org/sqlite, a pure-Go driver that needs no cgo.
provides:
  sql-dialect: sqlite
  conn: database/sql
  sql-schema: schema.sql
```

and `sqlc` accepts it with:

```yaml title="components/data/sqlc/component.yaml"
requires:
  sql-dialect: [sqlite, postgresql]
  conn: [database/sql]
  sql-schema: [schema.sql]
```

A selection is refused if a required trait is missing or has a value the
component does not accept, or if two components provide different values for
the same trait. Traits also carry the few facts one component needs about
another's files: `sqlc.yaml` finds the schema at
`{{.Slots.database.Dir}}/{{index .Traits "sql-schema"}}`. A component that
accepts several values of a trait may branch on the value, as sqlc does for
its query placeholder with `{{if eq (index .Traits "sql-dialect") "postgresql"}}`,
but never on another component's name. See [Traits](/docs/concepts/traits).

A component may accept several values of a trait and choose its code from the
value, never from the name of another component. `gorm` requires
`sql-dialect: [sqlite, postgresql]` and picks its GORM dialect in
`store.go.tmpl` with `{{if eq (index .Traits "sql-dialect") "postgresql"}}`,
so a new database that provides one of those values works with it unchanged.
Test every branch: `internal/compose` composes `gorm` with a test-only
PostgreSQL database, and the integration test builds that project too.

## Slots and contracts

Each slot is one directory, which means one Go package, and it has exactly one
owner. Two components can therefore never write into the same package or the
same file, and their identifiers cannot clash. The owner may put its own
subpackages below the slot directory; sqlc's generated code lives in
`internal/store/sqlcgen`, for example. Other slots never import them, unless
the contract names them: every database component provides a `dbtest`
subpackage whose `Open(t)` gives a test an empty database (and skips it when
the database needs a server that is not configured), so data-access
components test against whichever database is selected.

The architecture owns the entry point and the contract: the shared types and
the functions each slot must provide. For `mvc`, see the
[contract table](/docs/concepts/slots-and-contracts#architecture-owned-contracts).
The Go compiler checks the contract in every generated project, and gobento's
integration test checks that the handlers package does not depend on the
database or store packages.

All framework components serve the same API. Each one ships the same
`files/handlers/router_test.go.tmpl`, which tests the API only through
`NewRouter` and `net/http/httptest`, so it works with any router. Copy it
unchanged from an existing framework: a unit test fails if the copies differ.
To change the API, change every framework and the shared test together.

## Templates

Templates use Go's [`text/template`](https://pkg.go.dev/text/template). Every
template, including slot directories and notes, receives the same data:

| Field                   | Example                                    | Meaning                                                                                             |
| ----------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `.Project.Name`         | `shop`                                     | The project name                                                                                    |
| `.Project.Module`       | `example.com/shop`                         | The module path                                                                                     |
| `.Project.GoVersion`    | `1.27.0`                                   | The `go` directive of the generated `go.mod`                                                        |
| `.Slots.<name>.Dir`     | `internal/controllers`                     | The slot's directory                                                                                |
| `.Slots.<name>.Package` | `controllers`                              | The slot's package name                                                                             |
| `.Slots.<name>.Import`  | `example.com/shop/internal/controllers`    | The slot's import path                                                                              |
| `.Slots.<name>.Filled`  | `{{if .Slots.web.Filled}}`                 | Whether a selected component fills the slot                                                         |
| `.APIPrefix`            | `/api`                                     | Where the API router is served: `""` without a frontend, `/api` with one                            |
| `.Traits`               | `{{index .Traits "sql-dialect"}}`          | The traits of the selection                                                                         |
| `.Versions`             | `{{index .Versions "modernc.org/sqlite"}}` | The chosen version of each module                                                                   |
| `.Assets`               | `{{index .Assets "htmx.org"}}`             | The version of each [vendored asset](/docs/concepts/version-rules#vendored-assets) of the selection |

This data shape is the contributor API, and the golden test covers it. Use
`index` for keys that contain `-`, `.`, or `/`. A missing key is an error, not
an empty string, so `.Slots.handler` (a typo) fails composition.

A handler template therefore starts like this:

```go title="files/handlers/router.go.tmpl"
package {{.Slots.handlers.Package}}

import "{{.Slots.models.Import}}"

func NewRouter(items {{.Slots.models.Package}}.ItemStore) http.Handler {
```

Module paths contain dots, so read `.Versions` with `index`:

```text title="notes.md.tmpl"
go run github.com/sqlc-dev/sqlc/cmd/sqlc@{{index .Versions "github.com/sqlc-dev/sqlc"}} generate
```

### Rules for templates

- **No version numbers.** Versions come from `.Versions`, `.Assets`, and the
  rules file, never from a template. A vendored file, such as htmx, contains
  its own version, which is fine: it is shipped unmodified.
- **Write API paths with `.APIPrefix`.** In notes and READMEs, write
  `{{.APIPrefix}}/items`, so the paths are right with and without a frontend.
- **Implement your slot's contract.** Provide exactly the functions and types
  the architecture expects for your slot (see the
  [contract table](/docs/concepts/slots-and-contracts#architecture-owned-contracts)).
- **Import other slots only through the contract.** For example, handlers must
  not import the database or store packages, directly or transitively.
- **Use slot data, not directories.** Write `.Slots.store.Import`, never a
  hard-coded path, so your component works with any architecture.
- **Do not reuse package names as local names.** The contract package may be
  called `models` or `items`, depending on the architecture, so a variable
  named `items` would shadow it. Name local identifiers after their role,
  such as `list`, `got`, or `store`.
- **Produce valid, formatted Go.** Every `.go` output is run through
  `go/format`. A failure is reported as a composition error naming your
  component and the file. Generated files must also have no unused imports.
- **Leave `go.mod` and `go.sum` alone.** gobento writes them during
  generation; a component that produces either is rejected.

### README notes

If users need to know something about your component, add `notes.md.tmpl`.
Every component's rendered notes are appended to the root `README.md`, in kind
order. `nethttp` documents the API and its error responses, each database
starts with a `## Database` section (the architecture's README links to it)
that explains the default `DATABASE_URL`, the tests, and how the schema is
applied, `sqlc` shows how to regenerate its code, and `gorm` explains that the
schema file, not `AutoMigrate`, defines the tables.

### Composition errors

Composition reports every problem at once: unknown or unfilled slots, slots
with two owners or an owner of the wrong kind, two slots in one directory,
file conflicts, root files inside a slot directory, files written into a
slot nested inside their own slot's directory, components that produce
`go.mod` or `go.sum`, unmet traits, and templates that fail to render. See
[When composition fails](/docs/concepts/slots-and-contracts#when-composition-fails).

## Versions

Every module your component uses needs an entry in
[`components/versions.yaml`](https://github.com/Tales-of-zuna/gobento/blob/main/components/versions.yaml):

```yaml title="components/versions.yaml"
go:
  range: '>=1.26 <1.28'
  default: '1.27'
modules:
  modernc.org/sqlite:
    components: [database/sqlite]
    role: library
    range: '>=v1.61.0 <v2.0.0'
    default: v1.61.1
    constraints:
      - when: '>=v1.61.0'
        require: { go: '>=1.26' }
```

These are the values at the time of writing; the current ranges and defaults
are in the [Components reference](/docs/components).

- **`components`** lists every component that uses the module, as
  `<kind>/<name>`.
- **`traits`** (optional) limits the module to selections that provide one of
  the listed values for each listed trait, such as
  `traits: { sql-dialect: [postgresql] }` for a driver only one dialect needs.
  Otherwise the module is left out of `go.mod` and cannot be pinned. Prefer
  this over listing a module that some selections never import: gobento fails
  a generation in which a chosen library is not imported. See
  [Trait conditions](/docs/concepts/version-rules#trait-conditions).
- **`role`** is `library` for modules required in the generated `go.mod`;
  users may choose any version inside the range with `--pin`. It is `tool`
  for tools, such as sqlc, that are run with `go run` and never added to
  `go.mod`. A tool gets a single exact version, such as `=v1.31.1`, because
  tool versions are fixed per gobento release.
- **`range`** is a space-separated list of comparators (`>=`, `>`, `<=`, `<`,
  `=`) that must all hold. CI generates the project with both the default and
  the range floor, so the floor must really work.
- **`constraints`** apply when the module's chosen version is inside `when`,
  and then require `go` or another module to be inside a range, such as a
  minimum Go version.

A file that your component ships unmodified from an upstream release, such as
a JavaScript library, is not a module: record it under `assets` with its
`version`, the release archive as `source`, the file's `path` in it, and its
`sha256`. See [Vendored assets](/docs/concepts/version-rules#vendored-assets).
Asset versions are fixed per gobento release, and the tests compare the
checksum with your file and with the upstream one.

gobento rejects the generation if `go mod tidy` would raise any chosen version
or the `go` directive, and reports the missing constraint. See
[Version rules](/docs/concepts/version-rules) for the full format.

### Bumping a version

1. Change `default` (and `range`, if needed) in `versions.yaml`.
2. Run `make catalog` so the website shows the new values (`go test` fails
   until you do), then `make test` and
   `go test ./internal/generate -run TestIntegration` (it needs network
   access). The integration test generates every supported selection without
   a frontend, and a pairwise covering set of those with one, with the
   defaults and with the range floors.
3. If a template's output changes, update the golden files with
   `go test ./internal/compose -run TestGolden -update` and review the diff.

## Steps to add a component

<Steps>
<Step>

### Propose it

Open a [component request](https://github.com/Tales-of-zuna/gobento/issues/new?template=component_request.yml)
and, for a new kind of behavior, an OpenSpec change (see
[CONTRIBUTING.md](https://github.com/Tales-of-zuna/gobento/blob/main/CONTRIBUTING.md)).

</Step>
<Step>

### Write the manifest

Create `components/<kind>/<name>/component.yaml` with the traits it provides
and requires.

</Step>
<Step>

### Add the templates

Add templates under `files/<slot>/` for the slot its kind fills, and under
`files/root/` for project-root files. Implement the slot's contract and import
other slots only through the `models` contract.

</Step>
<Step>

### Add tests to the templates

Add `*_test.go.tmpl` files; they run in every generated project. Tests that
use files close them in `t.Cleanup`, because Windows cannot remove open files.

</Step>
<Step>

### Add its versions

Add the modules it uses to `versions.yaml`, with `components` naming it, and
`traits` for modules that only some trait values need.

</Step>
<Step>

### Regenerate the website catalog and test

Run `make catalog`, then `make lint test` and the integration test. Every
supported selection without a frontend that contains the new component is
generated, built, vetted, and tested; a new frontend is built with every
architecture, framework, database, and data access, and every pair of them.
`go run ./cmd/gobento list` shows the new component and its selections without
any change to the CLI.

</Step>
</Steps>

## Tests

<Steps>
<Step>

### Unit tests

The unit tests load the shipped catalog and rules file, enforce the `.tmpl`
rule, and check the list of supported selections. They catch an invalid
manifest, a default outside its range, or an unknown reference. They also
fail when the website's `catalog.json` is out of date (fix it with
`make catalog`), and they run every command the website's configurator offers
through `gobento new --dry-run`.

```sh
make test
```

</Step>
<Step>

### Golden test

The golden tests compose the reference selection of each architecture and
compare the whole project with `internal/compose/testdata/golden/` (`mvc`),
`internal/compose/testdata/golden-vertical-slice/` (`vertical-slice`), and
`internal/compose/testdata/golden-ddd/` (`ddd`), and the `mvc` one again with
htmx in `internal/compose/testdata/golden-htmx/`, which shows how the
architecture mounts a frontend. They also compose, for every component, the
first supported selection that contains it (with `mvc`, unless the component
is an architecture), and compare the files that component contributes with
`internal/compose/testdata/golden-components/<kind>/<name>/`. Another test
checks that every framework's files are the same under every architecture
apart from package names and import paths. A new component needs its golden
files, and an intended output change needs them refreshed. Regenerate them
and review the diff:

```sh
go test ./internal/compose -run TestGolden -update
```

</Step>
<Step>

### Integration test

The integration test in `internal/generate` generates the selections that
`compose.Coverage` returns twice, once with the default versions and once
with the range floors: every supported selection without a frontend, and of
those with a frontend, a set in which every pair of components that can
appear together with a frontend appears together at least once. Backend
combinations are thus all proven, and the frontend part grows with the
largest pair product instead of multiplying the matrix. For each project it
runs `go build`, `go vet`, `go test`, `gofmt -l`, `go mod verify`, and
`go build` again with `CGO_ENABLED=0` (generated projects must build without
a C compiler), checks the `go.mod` pins, and checks with `go list -deps` that
the handlers package, and the web package when there is one, do not import
the database or store packages, and that the web package imports no
framework module.

It needs network access and is skipped with `-short`. Run it with:

```sh
make test-all
```

CI runs it on Linux, macOS, and Windows. On Linux it also runs a PostgreSQL
service and sets `TEST_DATABASE_URL`, so tests that use a database server run
for real there instead of being skipped; see `CONTRIBUTING.md` to do the same
locally.

</Step>
</Steps>

### Generated code: sqlc

The `sqlc` component ships sqlc's generated code instead of running sqlc
during generation. After changing `queries.sql` or the schema, regenerate it
in a generated project with the pinned sqlc version (the command is in the
generated README), copy the files in `internal/store/sqlcgen/` back to
`components/data/sqlc/files/store/sqlcgen/` with the `.tmpl` suffix, and
update the golden files. The output differs between dialects only where the
templates branch on `sql-dialect` (the placeholder), so regenerate in one
project per database (`--db sqlite` and `--db postgres`) and keep those
branches in sync. CI's `sqlc-fresh` job does the same for each database and
fails if any file changes.

### Generated code: templ

The `htmx` frontend ships the Go code templ generates from `pages.templ`
(`pages_templ.go`). After changing `pages.templ.tmpl`, generate a project with
`--frontend htmx`, run `go generate ./...` in it (the `//go:generate` line in
the web package runs the pinned templ), and copy `pages_templ.go` back to
`components/frontend/htmx/files/web/pages_templ.go.tmpl`, replacing the
package name, the models import and package, the project name in `<title>`,
and `/api` with their template fields (`{{.Slots.web.Package}}`,
`{{.Slots.models.Import}}`, `{{.Slots.models.Package}}`, `{{.Project.Name}}`,
`{{.APIPrefix}}`). Keep template fields off lines with templ expressions, so
the line and column numbers templ records stay right. Then update the golden
files. CI's `templ-fresh` job regenerates the code in a reference project and
fails if any file changes. When you bump templ in `versions.yaml`, regenerate
in the same way.

To update htmx, replace `files/web/static/htmx.min.js.tmpl` with
`dist/htmx.min.js` of the new release, and change `version`, `source`, and
`sha256` of the `htmx.org` asset. The file is rendered as a template, so it
must not contain `{{`; the checksum test fails otherwise.

## Supporting frontends in an architecture

A frontend fills the `web` slot, so an architecture supports frontends by
declaring that slot and wiring it. Without these steps, selections with a
frontend are simply not supported with it. Both shipped architectures do the
following; copy them:

1. **Declare the slot.** Add an optional slot filled by the frontend kind,
   for example `web: { dir: internal/web, filled_by: frontend }`. Put it
   where pages and static files belong in your layout, outside any feature
   directory if the pages are shared.
2. **Build the handler in `newHandler`.** In the entry point, pass
   `newHandler(store.New(db))` to the server, and define it with
   `{{if .Slots.web.Filled}}`: with a frontend, an `http.ServeMux` that sends
   `{{.APIPrefix}}/` to
   `http.StripPrefix("{{.APIPrefix}}", handlers.NewRouter(itemStore))` and
   `/` to `web.NewHandler(itemStore)`; without one, `NewRouter(itemStore)`.
   Import the web package only inside the same condition.
3. **Ship the routing test.** Add `files/entry/main_test.go.tmpl`, which calls
   `newHandler` with an in-memory `ItemStore` and checks
   `{{.APIPrefix}}/health` and `{{.APIPrefix}}/items`, plus `/` returning HTML
   when the slot is filled. Copy it from `mvc`.
4. **Document it.** In the README template, add the web directory to the
   layout when the slot is filled, tell the reader to open
   `http://localhost:8080/`, and write the `curl` paths as
   `localhost:8080{{.APIPrefix}}/items`.
5. **Keep the contract.** The web slot's contract is
   `func NewHandler(items models.ItemStore) http.Handler`, with the same
   `models` package as the handlers. If your architecture's contract package
   differs, the frontend still only needs an `ItemStore` and an `Item` with
   `ID`, `Name`, and `CreatedAt`.

Then run `go test ./internal/compose -run TestGolden -update`; the
frontend's golden test and `TestShippedFrontendMount` check the wiring.

## Adding a frontend

A frontend fills the `web` slot and provides
`func NewHandler(items models.ItemStore) http.Handler`, serving `/` and every
other path outside `{{.APIPrefix}}/`. Use only the standard library's
`net/http` for routing, so it works with every framework, and reach the data
only through `ItemStore`. Serve its static files from the binary with
`//go:embed`, so the project works offline, and record any vendored file as an
[asset](#versions). Ship `*_test.go.tmpl` tests against a fake `ItemStore`, as
`htmx` does.

Frontends built by a JavaScript toolchain (React, Vue, or Svelte via Vite)
are planned: they will embed the built `dist/` directory with
`//go:embed all:dist`, serve `index.html` for client-side routes, call the API
under `{{.APIPrefix}}`, and configure Vite's dev server to proxy
`{{.APIPrefix}}` to the Go server.

## Documentation

You do not need to edit the docs to list your component. The
[Components reference](/docs/components) is generated from the catalog when
the site is built, including traits, versions, and defaults, once you have run
`make catalog`.
