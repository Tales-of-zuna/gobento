## What gobento is

gobento is a command-line tool that generates a new Go project from the stack
you pick: an architecture, an HTTP framework, a database, a data-access
library, and optionally a frontend.

```sh
gobento new shop --module example.com/shop --arch mvc --framework chi --db postgres --data sqlc
```

The generated project builds, passes `go vet` and `gofmt`, and passes its own
tests without any edits from you.

## Why it exists

Project generators often hard-code tool versions in their templates and grow
one template per combination of options. They fall behind upstream releases,
and every new option multiplies the work.

gobento avoids both problems:

- **Your stack, your choice.** You select one component of each kind, and a
  frontend only if you want one. Flags are only required when a required kind
  has more than one option.
- **Versions as data.** All supported Go and module versions live in one rules
  file. You can choose versions inside the supported ranges, and gobento
  rejects combinations that do not work instead of silently changing them.
- **Composed, not copy-pasted.** An architecture defines slots with Go
  contracts between them, and components fill the slots. There is no template
  per combination.
- **Safe to run anywhere.** Every input problem is reported at once, before
  anything is written. gobento only fills a new or empty directory, and on any
  failure or Ctrl-C it leaves nothing behind.
- **Proven builds.** Every supported backend combination is generated, built,
  and tested in CI on Linux, macOS, and Windows, and the combinations with a
  frontend are covered pairwise.

gobento is inspired by [go-blueprint](https://github.com/melkeydev/go-blueprint),
which showed how much a good project generator helps Go developers get
started.

## What you can choose today

| Kind           | Components                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| Architecture   | `mvc` (Model-View-Controller, by layer), `vertical-slice` (by feature), or `ddd` (domain-driven design) |
| HTTP framework | `nethttp` (the standard library's `net/http`), `chi`, `gin`                                             |
| Database       | `sqlite` (pure Go, no cgo), `postgres` (PostgreSQL through pgx, pure Go)                                |
| Data access    | `sqlc` or `gorm` (GORM)                                                                                 |
| Frontend       | none (API only, the default) or `htmx` (htmx + templ pages)                                             |

Every architecture uses the same framework, database, and data-access
components, arranged in a different layout, and every framework serves
exactly the same API. Every combination generates a project with a health
endpoint and one example resource, `/items`, stored in the database you
chose. With `--frontend htmx`, it also serves a page at `/` that lists and
adds items, and the API moves under `/api`. More architectures and frontends
(React, Vue, and Svelte via Vite) are on the roadmap; the
[Components](/docs/components) reference always lists exactly what the
catalog supports, and [`gobento list`](/docs/cli/list) shows the same from the
command line.
