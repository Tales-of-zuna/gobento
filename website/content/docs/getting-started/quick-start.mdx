Install gobento first, with
`go install github.com/Tales-of-zuna/gobento/cmd/gobento@latest` or a prebuilt binary from
[GitHub Releases](https://github.com/Tales-of-zuna/gobento/releases); see
[Installation](/docs/getting-started/installation) for checksums and details.

This guide generates a project called `shop` with MVC, `net/http`, SQLite, and
sqlc. Swap `--framework nethttp` for `chi` or `gin` to use another router; the
generated API is the same. SQLite needs no database server;
[Use PostgreSQL](#use-postgresql) shows what changes with `--db postgres`,
[With GORM](#with-gorm) what changes with `--data gorm`, and
[With htmx](#with-htmx) how to add web pages with `--frontend htmx`.

## Generate and run it

<Steps>
<Step>

### Preview the project (optional)

`--dry-run` validates your input and lists the files that would be created. It
writes nothing and does not run the Go toolchain.

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc --dry-run
```

It prints `Dry run: nothing was written.`, the module, the selection
(`mvc/nethttp/sqlite/sqlc, Go 1.27`), and the file list shown in
[What gets generated](#what-gets-generated).

</Step>
<Step>

### Generate it

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc
```

`--arch` chooses the architecture: `mvc` organizes the code by layer, and
`vertical-slice` by feature (see
[With the vertical-slice architecture](#with-the-vertical-slice-architecture)).
`--framework` picks the HTTP framework: `nethttp` (the standard library),
`chi`, or `gin`. `--db` picks the database: `sqlite` or `postgres` (see
[Use PostgreSQL](#use-postgresql)). `--data` picks the data access: `sqlc` or
`gorm` (see [With GORM](#with-gorm)). There is no `--frontend`, so the project
is an HTTP API (see [With htmx](#with-htmx) for web pages). If you leave out
one of these flags in a terminal, gobento asks you to choose; you can also run
plain `gobento new` and answer the questions for the name, module path, and
components. The same command with every choice spelled out, which never asks
anything (an omitted `--frontend` means none), is:

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc
```

gobento creates `./shop`, fetches the exact dependency versions with your Go
toolchain, and prints the next commands to run:

```text
Created example.com/shop in shop.

Next steps:
  cd shop
  go test ./...
  go run ./cmd/shop
```

</Step>
<Step>

### Run the tests

```sh
cd shop
go test ./...
```

The project builds, passes `go vet` and `gofmt -l`, and passes its own tests
without edits: the handlers are tested against a fake store, the entry point's
routing against an in-memory store, and the database and store packages
against a real SQLite database.

</Step>
<Step>

### Start the server

The server listens on the port in `PORT` (default `8080`) and stores its data
in the SQLite file named by `DATABASE_URL` (default `shop.db`, in the current
directory). This example sets the port explicitly.

<Tabs items={['macOS / Linux', 'Windows (PowerShell)']}>
<Tab value="macOS / Linux">

```sh
PORT=8080 go run ./cmd/shop
```

</Tab>
<Tab value="Windows (PowerShell)">

```powershell
$env:PORT = "8080"
go run ./cmd/shop
```

</Tab>
</Tabs>

</Step>
<Step>

### Call the API

In a second terminal:

```sh
curl -i http://localhost:8080/health
curl -i -X POST http://localhost:8080/items -d '{"name":"onigiri"}'
curl -i http://localhost:8080/items
```

The API has three routes. Every response is JSON:

| Request                                 | Response                                                                                                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /health`                           | `200` with `{"status":"ok"}`                                                                                                             |
| `POST /items` with `{"name":"onigiri"}` | `201` with the created item, such as `{"id":1,"name":"onigiri","created_at":"2026-11-03T06:15:11Z"}`                                     |
| `GET /items`                            | `200` with every item, oldest first, such as `[{"id":1,"name":"onigiri","created_at":"2026-11-03T06:15:11Z"}]`; `[]` when there are none |

`POST /items` takes exactly one JSON object with a non-empty `name` (leading
and trailing spaces are removed). Errors are JSON objects with an `error`
field:

| Request                                               | Response                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- |
| `{"name":""}` or `{"name":"  "}`                      | `400` `{"error":"name is required"}`                                         |
| Not JSON, or an unknown field such as `{"title":"x"}` | `400` `{"error":"invalid JSON body; send {\"name\": \"...\"}"}`              |
| More data after the object, such as `{"name":"a"} {}` | `400` `{"error":"invalid JSON body; unexpected data after the JSON object"}` |
| A body larger than 1 MiB                              | `413` `{"error":"request body is too large"}`                                |
| A storage failure                                     | `500` `{"error":"internal server error"}`; the details are logged, not sent  |

The generated README documents the same API.

</Step>
</Steps>

Each directory is one Go package, filled by one component:

| Path                                          | Filled by     | Contents                                                                                                                                                                                  |
| --------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cmd/shop/`                                   | architecture  | Config from the environment (`PORT`, default `8080`; `DATABASE_URL`, default `database.DefaultURL`, here `shop.db`), wiring, graceful shutdown on Ctrl-C or `SIGTERM`, and a routing test |
| `internal/models/`                            | architecture  | The `Item` type and the `ItemStore` interface                                                                                                                                             |
| `internal/controllers/`                       | framework     | `NewRouter` with `GET /health`, `GET /items`, and `POST /items`, and tests with a fake `ItemStore`                                                                                        |
| `internal/database/`                          | database      | `Open`, `DefaultURL`, an embedded `schema.sql` applied at startup, and `dbtest`, which gives each test an empty database                                                                  |
| `internal/store/`                             | data access   | `queries.sql`, the `New` adapter, and a test against a real database; sqlc's generated code is in the `sqlcgen` subpackage                                                                |
| `sqlc.yaml`                                   | data access   | sqlc configuration                                                                                                                                                                        |
| `README.md`, `.gitignore`, `go.mod`, `go.sum` | project files | `go.mod` is rendered by gobento, `go.sum` comes from the Go toolchain, and the README includes notes from each component                                                                  |

`go.mod` requires every direct dependency at an exact version: the defaults
from the [version rules](/docs/concepts/version-rules), or the versions you
chose with `--go` and `--pin`.

The sqlc output in `internal/store/sqlcgen` is shipped pre-generated, so you
do not need sqlc to build the project. The generated README explains how to
regenerate it with the pinned sqlc version (v1.31.1 today) after you change
`queries.sql` or the schema:

```sh
go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate
```

The schema in `internal/database/schema.sql` is embedded in the binary and
applied every time the server starts. It uses `CREATE TABLE IF NOT EXISTS`, so
it creates missing tables but never changes existing ones; it is not a
migration system.

## With the vertical-slice architecture

`--arch vertical-slice` generates the same files from the same components, in
a layout organized by feature:

```sh
gobento new shop --module example.com/shop --arch vertical-slice --framework nethttp --db sqlite --data sqlc
```

| Path                          | Filled by    | Contents                                                                               |
| ----------------------------- | ------------ | -------------------------------------------------------------------------------------- |
| `cmd/shop/main.go`            | architecture | The same entry point and wiring                                                        |
| `internal/items/`             | architecture | The items feature: the `Item` type and the `ItemStore` interface (`items.go`)          |
| `internal/items/itemshttp/`   | framework    | The feature's handlers, `NewRouter` with `/health`, and their tests                    |
| `internal/items/itemsstore/`  | data access  | The feature's `queries.sql`, the `New` adapter, its test, and the `sqlcgen` subpackage |
| `internal/platform/database/` | database     | `Open` and `schema.sql`, shared by every feature                                       |

The generated README explains the layout and how to add a second feature,
such as `internal/orders`, beside `internal/items`.

## Use PostgreSQL

Generate the same project on PostgreSQL with `--db postgres`: --data sqlc

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db postgres --data sqlc
```

The files are the same, except that `internal/database` opens PostgreSQL
through [pgx](https://github.com/jackc/pgx), a pure-Go driver, and
`sqlc.yaml` uses sqlc's `postgresql` engine. What changes for you:

- **Running the server.** `DATABASE_URL` defaults to
  `postgres://postgres:postgres@localhost:5432/shop?sslmode=disable`, a local
  development server. The generated README has a command that starts one with
  Docker:

  ```sh
  docker run --rm -d --name shop-postgres -p 5432:5432 \
    -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=shop postgres:18-alpine
  go run ./cmd/shop
  ```

  For any other server, set `DATABASE_URL` to its URL.

- **Running the tests.** `go test ./...` passes without a server: the
  database and store tests are skipped. Set `TEST_DATABASE_URL` to run them
  against a server. Each test works in a schema of its own, which it drops
  when it ends:

  ```sh
  TEST_DATABASE_URL='postgres://postgres:postgres@localhost:5432/shop?sslmode=disable' go test ./...
  ```

## With GORM

`gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data gorm` generates the same
project with a [GORM](https://gorm.io/) store. `internal/store/` then holds
only `store.go` (the `New` adapter, which wraps the `*sql.DB` from
`internal/database`) and `store_test.go` (a test against real SQLite), and
there is no `sqlc.yaml`. `go.mod` adds `gorm.io/gorm` and
`github.com/libtnb/sqlite`, a pure-Go GORM dialect on the same
`modernc.org/sqlite` driver, so the project still builds without cgo. The
tables still come only from `schema.sql`: the store never calls
`AutoMigrate`.

## With htmx

Add `--frontend htmx` to serve web pages next to the API, rendered on the
server from [templ](https://templ.guide) components and made interactive with
[htmx](https://htmx.org):

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc --frontend htmx
cd shop
go run ./cmd/shop
```

Open [http://localhost:8080/](http://localhost:8080/): the page lists the items and has a form that
adds one without reloading the page. The form also works with JavaScript
turned off (it posts, and the browser is redirected back to the page). The
JSON API is unchanged but moves under `/api`, so the frontend owns every other
path:

```sh
curl -i http://localhost:8080/api/health
curl -i -X POST http://localhost:8080/api/items -d '{"name":"onigiri"}'
curl -i http://localhost:8080/
```

The project gains one package, `internal/views` (`internal/web` with
`--arch vertical-slice`):

| Path                                | Contents                                                                                            |
| ----------------------------------- | --------------------------------------------------------------------------------------------------- |
| `internal/views/handler.go`         | `NewHandler`, serving `GET /`, `POST /items` (the form), and `/static/`; tests in `handler_test.go` |
| `internal/views/pages.templ`        | The page, the item row, and the form as templ components                                            |
| `internal/views/pages_templ.go`     | The Go code templ generates from `pages.templ`, shipped so that you need no templ command to build  |
| `internal/views/static/htmx.min.js` | htmx, vendored and embedded in the binary: the pages load nothing from a CDN and work offline       |
| `internal/views/static/styles.css`  | Plain CSS, no build step                                                                            |

`cmd/shop/main.go` mounts the API router under `/api/` and the pages at `/`.
`go.mod` adds `github.com/a-h/templ`, the templ runtime. After you edit
`pages.templ`, regenerate `pages_templ.go` with the pinned templ version; the
`//go:generate` line in `handler.go` holds the exact command:

```sh
go generate ./...
```

A blank name is answered with `422` and a message next to the field, and form
posts from other sites are rejected with `403`.
