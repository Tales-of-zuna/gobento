Install gobento first, with
`go install github.com/Tales-of-zuna/gobento/cmd/gobento@latest` or a prebuilt binary from
[GitHub Releases](https://github.com/Tales-of-zuna/gobento/releases); see
[Installation](/docs/getting-started/installation) for checksums and details.

This guide generates a project called `shop` with the first supported stack:
MVC, `net/http`, SQLite, and sqlc.

## Generate and run it

<Steps>
<Step>

### Preview the project (optional)

`--dry-run` validates your input and lists the files that would be created. It
writes nothing and does not run the Go toolchain.

```sh
gobento new shop --module example.com/shop --dry-run
```

It prints `Dry run: nothing was written.`, the module, the selection
(`mvc/nethttp/sqlite/sqlc, Go 1.27`), and the file list shown in
[What gets generated](#what-gets-generated).

</Step>
<Step>

### Generate it

```sh
gobento new shop --module example.com/shop
```

Each component kind has one option today, so gobento selects them for you.
When a kind has several options and you leave out its flag, gobento asks you
to choose in the terminal. You can also run plain `gobento new` and answer
the questions for the name, module path, and components. The same command
with every choice spelled out, which never asks anything, is:

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc
```

gobento creates `./shop`, fetches the exact dependency versions with your Go
toolchain, and prints the next commands to run:

```text
Created example.com/shop in shop.

Next steps:
  cd shop
  go test ./...
  go run ./cmd/shop
```

</Step>
<Step>

### Run the tests

```sh
cd shop
go test ./...
```

The project builds, passes `go vet` and `gofmt -l`, and passes its own tests
without edits: the handlers are tested against a fake store, and the database
and store packages against a real SQLite database.

</Step>
<Step>

### Start the server

The server listens on the port in `PORT` (default `8080`) and stores its data
in the SQLite file named by `DATABASE_URL` (default `shop.db`, in the current
directory). This example sets the port explicitly.

<Tabs items={['macOS / Linux', 'Windows (PowerShell)']}>
<Tab value="macOS / Linux">

```sh
PORT=8080 go run ./cmd/shop
```

</Tab>
<Tab value="Windows (PowerShell)">

```powershell
$env:PORT = "8080"
go run ./cmd/shop
```

</Tab>
</Tabs>

</Step>
<Step>

### Call the API

In a second terminal:

```sh
curl -i http://localhost:8080/health
curl -i -X POST http://localhost:8080/items -d '{"name":"onigiri"}'
curl -i http://localhost:8080/items
```

The API has three routes. Every response is JSON:

| Request                                 | Response                                                                                                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /health`                           | `200` with `{"status":"ok"}`                                                                                                             |
| `POST /items` with `{"name":"onigiri"}` | `201` with the created item, such as `{"id":1,"name":"onigiri","created_at":"2026-11-03T06:15:11Z"}`                                     |
| `GET /items`                            | `200` with every item, oldest first, such as `[{"id":1,"name":"onigiri","created_at":"2026-11-03T06:15:11Z"}]`; `[]` when there are none |

`POST /items` takes exactly one JSON object with a non-empty `name` (leading
and trailing spaces are removed). Errors are JSON objects with an `error`
field:

| Request                                               | Response                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------- |
| `{"name":""}` or `{"name":"  "}`                      | `400` `{"error":"name is required"}`                                         |
| Not JSON, or an unknown field such as `{"title":"x"}` | `400` `{"error":"invalid JSON body; send {\"name\": \"...\"}"}`              |
| More data after the object, such as `{"name":"a"} {}` | `400` `{"error":"invalid JSON body; unexpected data after the JSON object"}` |
| A body larger than 1 MiB                              | `413` `{"error":"request body is too large"}`                                |
| A storage failure                                     | `500` `{"error":"internal server error"}`; the details are logged, not sent  |

The generated README documents the same API.

</Step>
</Steps>

Each directory is one Go package, filled by one component:

| Path                                          | Filled by     | Contents                                                                                                                                  |
| --------------------------------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `cmd/shop/main.go`                            | architecture  | Config from the environment (`PORT`, default `8080`; `DATABASE_URL`, default `shop.db`), wiring, graceful shutdown on Ctrl-C or `SIGTERM` |
| `internal/models/`                            | architecture  | The `Item` type and the `ItemStore` interface                                                                                             |
| `internal/controllers/`                       | framework     | `NewRouter` with `GET /health`, `GET /items`, and `POST /items`, and tests with a fake `ItemStore`                                        |
| `internal/database/`                          | database      | `Open`, and an embedded `schema.sql` applied at startup                                                                                   |
| `internal/store/`                             | data access   | `queries.sql`, the `New` adapter, and a test against real SQLite; sqlc's generated code is in the `sqlcgen` subpackage                    |
| `sqlc.yaml`                                   | data access   | sqlc configuration                                                                                                                        |
| `README.md`, `.gitignore`, `go.mod`, `go.sum` | project files | `go.mod` is rendered by gobento, `go.sum` comes from the Go toolchain, and the README includes notes from each component                  |

`go.mod` requires every direct dependency at an exact version: the defaults
from the [version rules](/docs/concepts/version-rules), or the versions you
chose with `--go` and `--pin`.

The sqlc output in `internal/store/sqlcgen` is shipped pre-generated, so you
do not need sqlc to build the project. The generated README explains how to
regenerate it with the pinned sqlc version (v1.31.1 today) after you change
`queries.sql` or the schema:

```sh
go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate
```

The schema in `internal/database/schema.sql` is embedded in the binary and
applied every time the server starts. It uses `CREATE TABLE IF NOT EXISTS`, so
it creates missing tables but never changes existing ones; it is not a
migration system.
