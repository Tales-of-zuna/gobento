A **component** is one piece of a generated project: an architecture, an HTTP
framework, a database, a data-access library, or a frontend. Components are data (a
`component.yaml` manifest plus `.tmpl` template files), not Go code inside
gobento.

## The five kinds

| Kind           | Flag          | What it contributes                                                                                                       | Options                                |
| -------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Architecture   | `--arch`      | The project layout (its [slots](/docs/concepts/slots-and-contracts)), the entry point, and the Go contracts between slots | `mvc`, `vertical-slice`, `ddd`         |
| HTTP framework | `--framework` | The router and HTTP handlers                                                                                              | `nethttp`, `chi`, `gin`                |
| Database       | `--db`        | Opening the database connection and applying the schema                                                                   | `sqlite`, `postgres`                   |
| Data access    | `--data`      | The store that implements the data contract on top of the database                                                        | `sqlc`, `gorm`                         |
| Frontend       | `--frontend`  | Optional. Web pages served at `/`, next to the API, which then moves under `/api`                                         | none, `htmx`, `react`, `vue`, `svelte` |

## A selection

A **selection** is one component of each kind. It always contains exactly one
architecture, one framework, one database, and one data-access component, and
at most one frontend. The frontend is an **optional kind**: a selection
without one is an API-only project, and `none` stands for "no frontend" (no
component of an optional kind may be called `none`).

You choose with the flags above. If you omit a flag:

- and the kind has exactly one supported option, gobento selects it for you;
- and the kind has several options, gobento asks you to choose one when it
  runs in a terminal, offering only the options that work with your other
  choices;
- otherwise (in scripts and CI, or with `--no-input`), gobento stops, names
  the flag, and lists the supported values.

An omitted `--frontend` is different: it means no frontend, so the flag is
never required. In a terminal, gobento still asks, with "None (API only)"
first.

Today every required kind has several options, so name all four in scripts,
and add `--frontend` when you want one:

```sh
gobento new shop --arch vertical-slice --framework chi --db postgres --data gorm
gobento new shop --arch vertical-slice --framework chi --db postgres --data gorm --frontend htmx
```

## Scaffolded components

A component's files are normally all gobento templates. The React, Vue, and
Svelte frontends are different: their framework already has an official
scaffolder, Vite's `create-vite`, so gobento runs it instead of keeping a
copy of its templates. During generation, `npm create vite` creates
`frontend/` with the component's template (`react-ts`, `vue-ts`, or
`svelte-ts`), and the component adds only what must be gobento's: the Vite
configuration, the example page, the API client, the stylesheet, and the Go
web package that serves the build. gobento's files win where both write the
same path, and npm records the dependency tree in
`frontend/package-lock.json`.

Such a component names its scaffolder in its manifest, and the scaffolder's
version is in the [version rules](/docs/concepts/version-rules#nodejs-and-npm),
like every other version. Only these components need
[Node.js](/docs/getting-started/installation#nodejs-for-react-vue-and-svelte)
at generation time; `--dry-run` lists gobento's files and says what the
scaffolder adds.

## Supported selections

Not every selection can be built. A selection is **supported** exactly when:

1. it has one component of each required kind and at most one of each optional kind,
2. every trait a component requires is provided (see [Traits](/docs/concepts/traits)), and
3. it passes composition (see [Slots and contracts](/docs/concepts/slots-and-contracts)).

The list of supported selections is derived from the component catalog alone.
Leaving out the frontend is a separate selection, so every supported backend
combination is supported both without a frontend and with each frontend that
composes with it.

CI generates, builds, and tests projects on Linux, macOS, and Windows, each
with the default versions and with the lowest version of every range:

- **every supported selection without a frontend**, so each backend
  combination is proven;
- of the selections with a frontend, a **pairwise covering set**: every two
  components that can appear together with a frontend (for example, the
  frontend and `gin`, or `vertical-slice` and `chi` with a frontend) are built
  together at least once. A frontend meets the rest of the project only
  through the architecture's contracts and the router it is mounted next to,
  so pairs cover the interactions, while the full product would multiply the
  matrix with every new frontend.

`compose.Coverage` computes this set from the catalog, deterministically, and
a unit test checks the pair property. The website's configurator reads the same list from the exported
catalog, and a test runs the command it builds for each one through
`gobento new --dry-run`.

## Where components live

Each component is a directory in the repository under
`components/<kind>/<name>/`. Its `component.yaml` has these keys, and unknown
keys are rejected:

| Key           | Kinds             | Meaning                                                                                                                                                                   |
| ------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | all               | Equal to the directory name; matches `^[a-z][a-z0-9-]*$`                                                                                                                  |
| `title`       | all               | Required display name, such as `SQLite`                                                                                                                                   |
| `description` | all               | Optional one-sentence summary                                                                                                                                             |
| `slots`       | architecture only | The [slots](/docs/concepts/slots-and-contracts) it declares                                                                                                               |
| `provides`    | all               | [Traits](/docs/concepts/traits) it provides: trait → value                                                                                                                |
| `requires`    | all               | Traits it needs from the others: trait → list of accepted values                                                                                                          |
| `scaffold`    | all               | Optional. The scaffolder from the rules file, its template, the directory it creates, and scaffolded files to remove; see [Scaffolded components](#scaffolded-components) |

## The base layer

Besides the four selected components, every selection gets gobento's **base
layer** (`components/base/`): the [project tooling](/docs/concepts/project-tooling),
such as the Makefile, the Dockerfile, and the CI workflow. It is not a kind,
has no flag, and only writes files at the project root; components extend
its files through contribution points instead of writing them.

To see every component with its traits and
versions, open the [Components reference](/docs/components), which is
generated from the catalog. To write one, see
[Adding a component](/docs/contributing/adding-a-component).
