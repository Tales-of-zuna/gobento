---
title: Version rules
description: How gobento describes supported Go and module versions as data, lets you choose within them, and guarantees what your go.mod gets.
---

All version data lives in one rules file, `components/versions.yaml`: Go and
module versions, and the [tooling versions](#tooling-versions) of images and
actions. Templates never contain version numbers, so a version bump is a
one-line, reviewable change.

## The rules file

```yaml title="components/versions.yaml"
go:
  range: '>=1.26 <1.28'
  default: '1.27'
modules:
  modernc.org/sqlite:
    components: [database/sqlite]
    role: library
    range: '>=v1.61.0 <v2.0.0'
    default: v1.61.1
    constraints:
      - when: '>=v1.61.0'
        require: { go: '>=1.26' }
  github.com/jackc/pgx/v5:
    components: [database/postgres]
    role: library
    range: '>=v5.12.0 <v6.0.0'
    default: v5.12.0
  github.com/sqlc-dev/sqlc:
    components: [data/sqlc]
    role: tool # not in go.mod; fixed per gobento release
    range: '=v1.31.1'
    default: v1.31.1
```

<Callout type="info">
  This is the rules file at the time of writing. The [Components reference](/docs/components) is
  generated from the real file, so it always shows the current ranges and defaults.
</Callout>

| Field                    | Meaning                                                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `go.range`, `go.default` | The Go versions a generated project may use, and the one used by default                                               |
| `modules.<path>`         | One entry per Go module, keyed by module path                                                                          |
| `components`             | The components that use the module, as `<kind>/<name>`                                                                 |
| `traits`                 | Optional. Trait values the selection must provide for the module to be used; see [Trait conditions](#trait-conditions) |
| `role`                   | `library` (required in the generated `go.mod`) or `tool` (used but not in `go.mod`)                                    |
| `range`                  | The supported versions                                                                                                 |
| `default`                | The version used when you do not choose one; it must lie inside `range`                                                |
| `constraints`            | Conditions on other versions; each applies `when` the module's version matches, and states what it `require`s          |

## Trait conditions

Some modules are needed only for one value of a [trait](/docs/concepts/traits).
GORM, for example, needs a different driver per SQL dialect. Such a module
lists `traits`:

```yaml title="components/versions.yaml"
github.com/libtnb/sqlite:
  components: [data/gorm]
  traits: { sql-dialect: [sqlite] }
  role: library
  range: '>=v1.1.0 <v2.0.0'
  default: v1.2.2
gorm.io/driver/postgres:
  components: [data/gorm]
  traits: { sql-dialect: [postgresql] }
  role: library
  range: '>=v1.6.1 <v2.0.0'
  default: v1.6.3
```

A module is used when one of its `components` is selected and, for every
trait it lists, the selection provides one of the listed values. A module that
is not used is not added to `go.mod`, its constraints do not apply, and
`--pin` rejects it like any other module the selection does not use. So
`gobento new shop --db sqlite --data gorm` requires `github.com/libtnb/sqlite`
but not `gorm.io/driver/postgres`.

Conditions name traits, not components, so a new database that provides
`sql-dialect: postgresql` gets the PostgreSQL driver without a change to the
rules file. Loading fails if a condition names a trait that no component
provides.

## Ranges

A range is a space-separated list of comparators, all ANDed together:

| Comparator  | Meaning      |
| ----------- | ------------ |
| `>=v1.61.0` | at least     |
| `>v1.61.0`  | greater than |
| `<=v1.61.0` | at most      |
| `<v2.0.0`   | less than    |
| `=v1.31.1`  | exactly      |

So `">=v1.61.0 <v2.0.0"` means "v1.61.0 or newer, but older than v2.0.0".
Versions are compared as semantic versions (with `golang.org/x/mod/semver`).
Go versions are written without a `v` and normalized internally: `1.27` is
compared as `v1.27.0`.

## Defaults and overrides

gobento resolves versions in this order:

1. Start from the defaults: the default Go version and the default of every
   library module the selection uses.
2. Apply your overrides: `--go` for the Go version, and `--pin module=version`
   for library modules.
3. Check every version against its range.
4. Evaluate every constraint whose `when` matches.

Every problem from steps 3 and 4 is collected and reported together.

```sh
gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --go 1.26 --pin modernc.org/sqlite=v1.61.0
```

`--pin` is rejected when:

- the version is outside the module's range (the error shows the range);
- no selected component uses the module, or its trait conditions are not met
  (the error names it);
- the module is a tool (the error shows the version this release uses).

See [Errors](/docs/cli/new#errors) for the exact messages.

## Tool versions are fixed

Tool modules, such as sqlc, have an exact range. Their version is fixed per
gobento release and cannot be changed with `--pin`.

sqlc's output is generated ahead of time and shipped with the component, so
generating a project does not compile or run sqlc. The generated README shows
how to regenerate the code with the pinned version:

```sh
go run github.com/sqlc-dev/sqlc/cmd/sqlc@<version> generate
```

templ, used by the htmx frontend, is the same idea in library form: the
generated code imports the templ runtime, so `github.com/a-h/templ` is a
library in `go.mod`, but its range is exact (`=v0.3.1100`) because the
component ships the code that version generates. Bump the version together
with that code.

## Vendored assets

Some components ship a file that is not Go code and not a Go module, such as
the htmx JavaScript library the htmx frontend serves from the binary. Such a
file is an **asset**, recorded in the same rules file:

```yaml title="components/versions.yaml"
assets:
  htmx.org:
    components: [frontend/htmx]
    version: 2.0.11
    source: https://registry.npmjs.org/htmx.org/-/htmx.org-2.0.11.tgz
    path: package/dist/htmx.min.js
    sha256: d6fdc75f204e6bdefa99b69bf1e6d4ac69b8a364f77929f45c13476b4000f717
```

| Key          | Meaning                                              |
| ------------ | ---------------------------------------------------- |
| `components` | The components that ship the file                    |
| `version`    | The upstream release, such as `2.0.11`               |
| `source`     | The `https` URL of the release archive (a `.tgz`)    |
| `path`       | The file's path inside that archive                  |
| `sha256`     | The file's SHA-256 checksum, 64 lowercase hex digits |

The component ships the file unmodified, so a project needs no network
access to get it, at generation or at run time. Like a tool, an asset is fixed
per gobento release and cannot be pinned. Templates can name its version, as
in `{{index .Assets "htmx.org"}}`, but never contain it.

gobento's tests check both ends: the file the component renders has the
recorded checksum, and, with network access, so does the file at `path` in
`source`. To update an asset, replace the file and change `version`,
`source`, and `sha256` together.

## Downloaded binaries

Some components need a program that is neither a Go module nor small enough
to vendor, such as the standalone Tailwind CSS CLI, a self-contained binary of
about 100 MB per platform that compiles Tailwind CSS without Node.js. Such a
program is a **binary**, recorded with a download for each platform:

```yaml title="components/versions.yaml"
binaries:
  tailwindcss:
    components: [css/tailwind]
    version: 4.3.4
    checksums: https://github.com/tailwindlabs/tailwindcss/releases/download/v4.3.4/sha256sums.txt
    platforms:
      linux/amd64:
        url: https://github.com/tailwindlabs/tailwindcss/releases/download/v4.3.4/tailwindcss-linux-x64
        sha256: 149a8ece5b855587a9c10de6da9dcbcfad0e47c4ed5dca219f721b3eae39d817
      # darwin/amd64, darwin/arm64, linux/arm64, windows/amd64, windows/arm64
```

| Key                    | Meaning                                                                                          |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| `components`           | The components that use the binary                                                               |
| `version`              | The upstream release, such as `4.3.4`                                                            |
| `checksums`            | Optional. The `https` URL of the release's checksum file (`<sha256>  <file>` lines)              |
| `platforms`            | One entry per `GOOS/GOARCH` platform the release supports                                        |
| `platforms.<p>.url`    | The `https` URL of the file for that platform; it must contain the version                       |
| `platforms.<p>.sha256` | The file's SHA-256 checksum, 64 lowercase hex digits, which the project checks before running it |

A generated project downloads a binary only when a developer runs it (with
Tailwind CSS: `make generate` after a style change), never to build, test, or
run the project, and never at generation time. Like an asset, a binary is
fixed per gobento release and cannot be pinned. Templates read it as
`{{.Binaries.tailwindcss.Version}}` and range over
`{{.Binaries.tailwindcss.Platforms}}` (`.OS`, `.Arch`, `.URL`, `.SHA256`);
`css/tailwind` renders that table into the Go program that downloads, checks,
and runs the CLI. Loading the rules rejects a platform that is not
`GOOS/GOARCH`, a URL without the version, and a malformed checksum, and
gobento's tests compare every checksum with the release's `checksums` file
when they have network access. To update a binary, change `version`, every
URL, and every `sha256` together, from the release's checksum file.

## Tooling versions

The [project tooling](/docs/concepts/project-tooling) uses versions that are not
Go module requirements: container images, GitHub Actions, and golangci-lint.
They live in the `tooling` section of the same file:

```yaml title="components/versions.yaml"
tooling:
  images:
    go: # build stage of the Dockerfile
      image: golang
      tag: '{go}' # the selected Go version, for example 1.27
    runtime: # runtime stage, pinned by digest because it ships
      image: gcr.io/distroless/static-debian13
      tag: nonroot
      digest: sha256:25ac8f0c3b2334a9eb05452266bd4697864a8c8ef0ef71e5e6480d7f92868329
    postgres: # the CI service and the README's local server
      image: postgres
      tag: 18-alpine
  actions:
    actions/checkout:
      version: v7.0.1
      sha: 3d3c42e5aac5ba805825da76410c181273ba90b1
  tools:
    golangci-lint: v2.15.0
```

| Field                  | Meaning                                                                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `images.<key>`         | An image; templates read `{{.Images.<key>}}`, the full reference `image:tag`, followed by `@digest` when it has one              |
| `image`, `tag`         | The image name without tag, and the tag; `{go}` in a tag is the selected Go version, the only placeholder                        |
| `digest`               | Optional `sha256:` digest that pins the image                                                                                    |
| `actions.<owner/repo>` | A GitHub Action; templates read `{{index .Actions "<owner/repo>"}}`, the complete `uses:` value `<owner/repo>@<sha> # <version>` |
| `version`, `sha`       | The release and the full 40-character commit SHA its tag points to                                                               |
| `tools.<name>`         | An exact tool version, read as `{{index .Tools "<name>"}}`                                                                       |

gobento rejects a malformed name, tag, digest, version, or SHA when it loads
the file. Like tool modules, tooling versions are fixed per gobento release
and cannot be changed with `--pin`; the generated Dependabot configuration
keeps them current in your project, and
[`gobento list versions`](/docs/cli/list#versions) lists them. When you bump
one, check the SHA with `gh api repos/<owner/repo>/commits/<version>` and a
digest with `docker buildx imagetools inspect <image>:<tag>`, and update the
"Last checked" date in the file.

## Constraint errors

A constraint ties one version to another. In the example above, sqlite
`>=v1.61.0` requires Go `>=1.26`. If you choose a module version that needs a
newer Go than the one selected, gobento exits with status `1` and writes
nothing. The error names the module, its version, the required range, and the
selected version; if the rules allowed Go 1.25, choosing it would report:

```text
incompatible versions: modernc.org/sqlite v1.61.0 requires go >=1.26, but go 1.25 is selected
```

A constraint can also require another module (`require: { example.com/b: ">=v0.2.0" }`);
it applies only when that module is part of the selection.

## The rules file is checked

Loading fails, with an error naming the module, if the rules file:

- has an unknown field (a typo fails instead of being ignored),
- declares a default outside its own range,
- gives a tool a range other than one exact version, such as `=v1.31.1`,
- references an unknown component or constraint target,
- conditions a module on a trait that no component provides,
- contains a malformed range or version.

gobento's test suite checks the shipped rules file, and CI generates every
supported selection twice: once with the defaults and once with the range
floors. So every version a range claims to support is tested.

## How a range floor is chosen

A range floor is the oldest version gobento claims to support, and CI builds
it. It must exclude every release with a known advisory in the
[Go vulnerability database](https://vuln.go.dev), in the module itself or in
the dependency versions that release requires. For example, pgx's floor is
v5.12.0, although pgx's own advisories are fixed in v5.9.2: v5.9.2 to v5.11.0
require a version of `golang.org/x/text` with an advisory in code pgx uses.
The comment above each module in `versions.yaml` records why its floor is
where it is.

## Exact pinning

The generated `go.mod` contains exactly the chosen Go version and library
versions. Every direct dependency is an exact version, and `go mod verify`
succeeds.

## The MVS re-check

Go's dependency resolution (minimal version selection, MVS) can raise a
version on its own, for example when another dependency needs something newer.
gobento never accepts that silently:

1. It runs `go get` with every chosen version, then `go mod tidy`.
2. It parses the resulting `go.mod`. The `go` directive and every direct
   requirement must equal the chosen values.
3. If anything was raised, gobento exits with status `1` naming the module,
   the chosen version, and the raised version, and leaves no files behind. A raise
   means the rules file is missing a constraint, so please
   [open an issue](https://github.com/Tales-of-zuna/gobento/issues).

If your local toolchain adds a `toolchain` line to `go.mod`, gobento removes
it, so the project does not depend on the machine that generated it.
