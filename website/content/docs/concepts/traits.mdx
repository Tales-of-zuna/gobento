---
title: Traits
description: How components declare what they provide and require, so compatibility is decided by data instead of code.
---

A **trait** is a plain key/value fact about a component. Components never
depend on which other component is selected, only on the traits other
components provide.

## Provided and required traits

A component can **provide** traits, and it can **require** a trait to have one
of a list of values.

Both are keys of `component.yaml`. In the current catalog:

| Component             | `provides`                                                                | `requires`                                                                              |
| --------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `postgres` (database) | `sql-dialect: postgresql`, `conn: database/sql`, `sql-schema: schema.sql` | none                                                                                    |
| `sqlite` (database)   | `sql-dialect: sqlite`, `conn: database/sql`, `sql-schema: schema.sql`     | none                                                                                    |
| `gorm` (data access)  | none                                                                      | `sql-dialect: [sqlite, postgresql]`, `conn: [database/sql]`, `sql-schema: [schema.sql]` |
| `sqlc` (data access)  | none                                                                      | `sql-dialect: [sqlite, postgresql]`, `conn: [database/sql]`, `sql-schema: [schema.sql]` |

Trait names match `^[a-z][a-z0-9-]*$`. A provided value must not be empty,
and a requirement lists at least one accepted value.

## The traits in use

- **`sql-dialect`**: the SQL dialect the database speaks: `sqlite` or
  `postgresql`, the engine names sqlc uses. A data-access library that
  generates or runs SQL requires a dialect it supports. A component that
  accepts several dialects adapts to the provided one through the trait value,
  never through the database's name: sqlc's `sqlc.yaml` template says
  `engine: {{index .Traits "sql-dialect"}}`, and its pre-generated code picks
  the query placeholder (`?1` or `$1`) with
  `{{if eq (index .Traits "sql-dialect") "postgresql"}}`.
- **`conn`**: the Go type of the connection the database's `Open` returns,
  such as `database/sql`. The store's `New(db T)` must accept that type, so the
  data-access component requires a matching `conn`. See the
  [contract table](/docs/concepts/slots-and-contracts#architecture-owned-contracts).
- **`sql-schema`**: the file name of the schema inside the database slot,
  such as `schema.sql`. sqlc reads it to generate its code, so its
  `sqlc.yaml` template finds the schema at
  `{{.Slots.database.Dir}}/{{index .Traits "sql-schema"}}`. GORM uses the
  same tables without reading the file: it never calls `AutoMigrate`, so the
  schema stays the single source of truth. Traits carry the
  few facts one component needs about another's files, without naming the
  other component.

Future components declare their own values. For example, a database that
exposes pgx's native pool instead of `database/sql` would declare its own
`conn` value, so an incompatible pair is rejected by data, without any code in
gobento.

## Code that depends on a trait value

A component that accepts several values of a trait picks the matching code
from `.Traits` in its templates. `gorm` accepts `sql-dialect: sqlite` and
`postgresql`, and its store template chooses the GORM dialect accordingly:

```go title="components/data/gorm/files/store/store.go.tmpl"
{{if eq (index .Traits "sql-dialect") "postgresql"}}postgres.New(postgres.Config{Conn: db}){{else}}sqlite.New(sqlite.Config{Conn: db}){{end}}
```

Modules needed for only one value, such as each dialect's driver, carry a
[trait condition](/docs/concepts/version-rules#trait-conditions) in the rules
file, so a project's `go.mod` gets only the driver it uses. Because both the
template and the rules name trait values rather than components, a new
database that provides `sql-dialect: postgresql` works with `gorm` unchanged.

## When a trait is not met

If a selected component requires a trait that no selected component provides,
or a value it does not accept, gobento reports the trait and the components
involved, exits with status `1`, and writes nothing. Two components that
provide different values for the same trait are rejected the same way.

## Supported combinations

Traits decide which selections are **supported**. A selection is supported
exactly when it has one component per kind, every required trait is met, and
it [composes](/docs/concepts/slots-and-contracts#when-composition-fails)
without errors.

The set of supported selections is computed from the catalog alone. If the
catalog contained a data-access component whose required dialect no database
provides, no selection containing it would be listed as supported. The
website's configurator uses the same rules to disable incompatible options
and explain why.

Today every database provides what both data-access components require, so
all 36 candidate selections (3 architectures × 3 frameworks × 2 databases × 2
data-access components) are supported, for example:

```text
mvc + nethttp + postgres + gorm
mvc + nethttp + sqlite + sqlc
vertical-slice + nethttp + sqlite + sqlc
ddd + gin + postgres + sqlc
```

The [Components reference](/docs/components) lists the traits of every
component in the current catalog.
