## Synopsis

```text
gobento new [name] [flags]
```

`gobento new` generates a Go project called `<name>` from one architecture,
one HTTP framework, one database, and one data-access component, and
optionally one frontend. Every flag is optional in a terminal: gobento asks
for what is missing, including the name; see [Questions](#questions). In
scripts and CI, a component flag is required when its kind has several
supported components, except `--frontend`: without it, the project has no
frontend.

## Arguments

| Argument | Rules                                                                                                                                                                                                                                                                                                                                                                       |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<name>` | At most one; required unless gobento asks for it (see [Questions](#questions)). Starts with a lowercase letter and contains only lowercase letters, digits, `-`, and `_`. It must not be a name Windows reserves for devices: `con`, `prn`, `aux`, `nul`, `com1` to `com9`, or `lpt1` to `lpt9`. Used for the default directory, the default module path, and `cmd/<name>`. |

## Flags

| Flag           | Type                         | Default        | Description                                                                                                                                                                                                                     |
| -------------- | ---------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--module`     | string                       | `<name>`       | Go module path of the generated project, for example `example.com/shop`. It must be a valid Go import path, as checked by `module.CheckImportPath` from `golang.org/x/mod`. Paths without a dot, such as `shop`, are accepted.  |
| `--arch`       | string                       | auto           | Architecture component: `mvc` (by layer), `vertical-slice` (by feature), or `ddd` (domain-driven design). There are several, so it is asked for in a terminal and required otherwise.                                           |
| `--framework`  | string                       | auto           | HTTP framework component: `chi`, `gin`, or `nethttp`. There are several, so it is asked for in a terminal and required otherwise.                                                                                               |
| `--db`         | string                       | auto           | Database component: `sqlite` or `postgres`. There are several, so it is asked for in a terminal and required otherwise.                                                                                                         |
| `--data`       | string                       | auto           | Data-access component: `sqlc` or `gorm`. There are several, so it is asked for in a terminal and required otherwise.                                                                                                            |
| `--frontend`   | string                       | `none`         | Frontend component: `htmx` (htmx + templ pages), or `none` for an API-only project. Optional: asked for in a terminal ("None (API only)" first), never required. With a frontend, the API is served under `/api`.               |
| `--go`         | string                       | rules default  | Go version for the `go` directive, for example `1.26`. Must be inside the supported Go range.                                                                                                                                   |
| `--pin`        | `module=version`, repeatable | rules defaults | Version of a library module, for example `--pin modernc.org/sqlite=v1.61.0`. Must be inside the module's range, and a selected component must use the module. Tool modules and vendored assets (such as htmx) cannot be pinned. |
| `--dir`        | path                         | `./<name>`     | Directory to generate into, for example `.` for the current one. See [Output location](#output-location).                                                                                                                       |
| `--dry-run`    | bool                         | `false`        | Check the input and list the files that would be created, without writing anything. See [Dry run](#dry-run).                                                                                                                    |
| `--no-input`   | bool                         | `false`        | Never ask a question, even in a terminal. See [Questions](#questions).                                                                                                                                                          |
| `-h`, `--help` | bool                         | `false`        | Show the command's help.                                                                                                                                                                                                        |

**auto**: if the kind has exactly one supported component, it is selected. If
it has several, gobento asks for one in a terminal (see
[Questions](#questions)); otherwise it stops with a problem such as
`--arch: choose an architecture; supported: ddd, mvc, vertical-slice`.

**none**: the frontend is an optional kind. Without `--frontend`, or with
`--frontend none`, the project is an HTTP API whose routes are at `/`. With a
frontend, the frontend serves `/` and every other path outside `/api/`, and
the same API is served under `/api` (`/api/health`, `/api/items`). See
[Frontends](/docs/concepts/slots-and-contracts#frontends).

**rules default**: the default from the [version rules](/docs/concepts/version-rules).
The current defaults and ranges are listed in the [Components reference](/docs/components)
and by [`gobento list versions`](/docs/cli/list#versions).

`gobento --version` prints the gobento version: the release version for release binaries, the
module version for `go install` and builds from a clone (a pseudo-version between releases), and
`dev` when Go recorded no version, such as for `go run`. See
[Installation](/docs/getting-started/installation) for v0.1.0 installed with `go install`.

## Examples

These are the examples from `gobento new --help`.

Create `./shop` with mvc, the chi router, SQLite, sqlc, and the default versions:

```sh
gobento new shop --arch mvc --framework chi --db sqlite --data sqlc
```

Organize the code by feature instead of by layer, on PostgreSQL with GORM:

```sh
gobento new shop --arch vertical-slice --framework nethttp --db postgres --data gorm
```

Use domain-driven design: a domain, an application service, and adapters:

```sh
gobento new shop --arch ddd --framework gin --db sqlite --data sqlc
```

Add server-rendered pages with htmx and templ; the API moves under `/api`:

```sh
gobento new shop --arch mvc --framework chi --db sqlite --data sqlc --frontend htmx
```

Choose every component and the module path explicitly:

```sh
gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc
```

Choose versions within the supported ranges (here, the range floors):

```sh
gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --go 1.26 --pin modernc.org/sqlite=v1.61.0
```

Fill the current, empty directory:

```sh
mkdir shop && cd shop
gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --dir .
```

Show the files that would be created, without writing anything:

```sh
gobento new shop --arch mvc --framework gin --db sqlite --data sqlc --dry-run
```

Never ask a question, even in a terminal (as in scripts):

```sh
gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --no-input
```

## Questions

When stdin and stdout are both terminals, `gobento new` asks for what it
cannot decide by itself, before it checks or writes anything:

- **Project name**, when `<name>` is omitted, checked with the
  [name rules](#arguments). Then the **Go module path**; press Enter to use
  the name.
- **Each component kind** whose flag is omitted and that has several options,
  in the order architecture, framework, database, data access, frontend. Only
  options that form a [supported selection](/docs/concepts/components#supported-selections)
  with your flags and earlier answers are offered, so you cannot pick a
  combination that does not build. A kind left with one option is selected
  without a question. The frontend question offers "None (API only)" first,
  preselected.

Flags skip their questions: `gobento new shop` asks nothing about the name or
module path, and `--framework nethttp` skips the framework question. Versions
(`--go`, `--pin`) are never asked; the defaults come from the
[version rules](/docs/concepts/version-rules).

If a value you gave on the command line is invalid, such as
`--framework express` or a malformed `--pin`, gobento asks nothing and
reports every problem, as in [Errors](#errors).

After the questions, gobento prints the equivalent command on stderr, so you
can repeat the run in a script. A frontend answered with "None (API only)" is
left out, because that is what an omitted `--frontend` means:

```text
Equivalent command: gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc
```

`--dry-run` asks the same questions, then lists the files.

### Turning questions off

gobento never asks when stdin or stdout is not a terminal (pipes, CI, output
redirected to a file), or when you pass `--no-input`. It then behaves exactly
as without questions: `<name>` is required, a kind with several options needs
its flag, and no frontend is selected unless `--frontend` names one. On Windows, questions need a console such as Windows Terminal
or the classic console window; Git Bash's mintty is not one, so use flags
there or start gobento with `winpty`.

### Keys and cancelling

Use the arrow keys (or `j` and `k`) and Enter to choose, and type text
answers. Ctrl-C or Esc cancels: gobento prints
`gobento: interrupted; nothing was left behind`, writes nothing, and exits
with status `130`. If the input ends before the last answer (Ctrl-D in
accessible mode), gobento exits with status `1` and writes nothing.

### Accessible mode

Set `ACCESSIBLE` to any non-empty value to get plain, line-based questions
instead of the full-screen form, for example for screen readers. gobento also
uses this mode when `TERM=dumb`. Each question is a line of text, the options
of a choice are numbered, and you answer by typing a line:

```text
$ ACCESSIBLE=1 gobento new
Used for the directory, the default module path, and cmd/<name>; start with a lowercase letter and use only lowercase letters, digits, - and _.
Project name shop

For example example.com/shop; press Enter to use shop. Skip this question with --module.
Go module path example.com/shop
```

## What happens

1. **Validate.** The name, module path, selection, versions, and composition
   are all checked in memory. Every problem is collected and reported at once.
2. **Preflight.** gobento checks that `go` is on your `PATH`, compares the
   selected Go version with your toolchain, and checks the target directory.
3. **Write** the project and its `go.mod` into a temporary directory.
4. **Resolve** the exact versions with the Go toolchain (`go get`, then
   `go mod tidy`).
5. **Re-check** that `go.mod` contains exactly the chosen versions. See
   [the MVS re-check](/docs/concepts/version-rules#the-mvs-re-check).
6. **Place** the files in the target directory, and print the next commands
   to run.

Nothing is written before steps 1 and 2 pass. A successful run ends like this:

```text
$ gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc
Created example.com/shop in shop.

Next steps:
  cd shop
  go test ./...
  go run ./cmd/shop
```

## Output location

- The project is generated into `--dir` when given, otherwise into `./<name>`.
- If the target does not exist, it is created. Its parent directory must
  exist.
- If the target exists and is an empty directory, it is filled. This includes
  `.`, the current directory; the output then says
  `Created example.com/shop in the current directory.`
- If the target exists and is not empty, or is not a directory, gobento exits
  with status `1` and leaves it unchanged.

While working, gobento writes into a temporary directory named
`.gobento-tmp-<random>`: next to the target when the target does not exist
yet, or inside it when it is an existing empty directory. If generation fails
or you press Ctrl-C, gobento removes the temporary directory and anything it
already moved into the target. A target directory that existed before is
never deleted, and is left as it was.

## Dry run

`--dry-run` stops after validation and composition, which all happen in
memory. It lists every file that would be created, including `go.mod` and
`go.sum`, then exits.

```text
$ gobento new shop --module example.com/shop --arch mvc --framework nethttp --db sqlite --data sqlc --dry-run
Dry run: nothing was written.
gobento would create example.com/shop (mvc/nethttp/sqlite/sqlc, Go 1.27) in shop with these files:
  .gitignore
  README.md
  cmd/shop/main.go
  cmd/shop/main_test.go
  go.mod
  go.sum
  internal/controllers/items.go
  internal/controllers/router.go
  internal/controllers/router_test.go
  internal/database/database.go
  internal/database/database_test.go
  internal/database/dbtest/dbtest.go
  internal/database/schema.sql
  internal/models/models.go
  internal/store/queries.sql
  internal/store/sqlcgen/db.go
  internal/store/sqlcgen/models.go
  internal/store/sqlcgen/queries.sql.go
  internal/store/store.go
  internal/store/store_test.go
  sqlc.yaml
```

With `--arch vertical-slice`, the same files are listed under
`internal/items/`, `internal/items/itemshttp/`, `internal/items/itemsstore/`,
and `internal/platform/database/` instead. With `--arch ddd`, they are listed
under `internal/domain/`, `internal/adapters/httpapi/`,
`internal/adapters/persistence/`, and `internal/adapters/database/`, plus the
application service in `internal/app/items.go`, its test, and the domain's
test. With `--frontend htmx`, the
selection reads `mvc/nethttp/sqlite/sqlc/htmx`, and the list adds
`internal/views/handler.go`, `handler_test.go`, `pages.templ`,
`pages_templ.go`, `static/htmx.min.js`, and `static/styles.css` (under
`internal/web/` with `vertical-slice` and `internal/adapters/web/` with
`ddd`).

- It writes nothing and creates no directory.
- It does not run the Go toolchain, so it needs neither Go nor access to the
  Go module proxy.
- It does not check the target directory.
- It exits `0` for valid input. For invalid input, it reports the same
  validation and composition problems as a normal run and exits `1`.

## Environment

gobento runs every `go` command with `GOWORK=off`, and adds `-mod=mod` to
`GOFLAGS` (replacing any `-mod` flag you set; your other `GOFLAGS` are kept).
Everything else, such as `GOPROXY`, `GONOSUMDB`, and `GOPRIVATE`, is passed
through unchanged.

| Situation                                                                                                                     | Result                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| No `go` command on `PATH`                                                                                                     | Exits `1`, asking you to install Go from https://go.dev/dl/                             |
| Selected Go is newer than your toolchain, and `GOTOOLCHAIN` forbids downloads (`local`, `path`, or a value ending in `+path`) | Exits `1` naming both versions; install the newer Go or choose an older one with `--go` |
| Selected Go is newer than your toolchain otherwise                                                                            | Warns that the go command will download the selected Go, and continues                  |
| Fetching a module fails, for example without network                                                                          | Exits `1` with the underlying `go` error, and leaves no files behind                    |

## Exit status

| Status | Meaning                                                                                                                                                                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `0`    | The project was generated, or a dry run found no problems.                                                                                                                                                                     |
| `1`    | Any problem: invalid arguments or input, an unsupported selection, a version or constraint error, a failed preflight, or a failed `go` command. Nothing is left behind.                                                        |
| `130`  | Interrupted by Ctrl-C (or `SIGTERM`), or a question was cancelled with Ctrl-C or Esc. gobento removes everything it created and prints `gobento: interrupted; nothing was left behind`, or lists any file it could not remove. |

## Errors

gobento checks all input before it writes anything and lists every problem it
finds, one per line, so you can fix them all in one go. Problems with a
component flag start with the flag. This is the output for seven problems at
once; gobento's tests check that it matches the CLI exactly:

{/* several-problems */}

```text
$ gobento new "My App" --module "Not A Path" --arch mvc --framework express --go 1.20 --pin nonsense
gobento: cannot create "My App":
  - --pin "nonsense": want module=version, for example modernc.org/sqlite=v1.61.0
  - invalid project name "My App": start with a lowercase letter and use only lowercase letters, digits, - and _
  - invalid module path "Not A Path": malformed import path "Not A Path": invalid char ' '; use a path such as example.com/app
  - --framework: unknown framework "express"; supported: chi, gin, nethttp
  - --db: choose a database; supported: postgres, sqlite
  - --data: choose a data-access library; supported: gorm, sqlc
  - version outside the supported range: go 1.20; supported range is ">=1.26 <1.28"
```

A name reserved on Windows, which without `--module` is also the module path:

```text
$ gobento new con --arch mvc --framework nethttp --db sqlite --data sqlc
gobento: cannot create "con":
  - invalid project name "con": the name is reserved on Windows and cannot be used for files or directories; choose another name
  - invalid module path "con": malformed import path "con": "con" disallowed as path element component on Windows; use a path such as example.com/app
```

A module version outside its range:

```text
$ gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --pin modernc.org/sqlite=v2.0.0
gobento: cannot create "shop":
  - version outside the supported range: modernc.org/sqlite v2.0.0; supported range is ">=v1.61.0 <v2.0.0"
```

A tool version:

```text
$ gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --pin github.com/sqlc-dev/sqlc=v1.30.0
gobento: cannot create "shop":
  - version is fixed: cannot pin github.com/sqlc-dev/sqlc, tool versions are fixed per gobento release (this release uses v1.31.1)
```

A vendored asset, such as htmx, whose version is fixed like a tool's:

```text
$ gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --frontend htmx --pin htmx.org=v2.0.10
gobento: cannot create "shop":
  - version is fixed: cannot pin htmx.org, vendored asset versions are fixed per gobento release (this release ships 2.0.11)
```

An unknown frontend; `none` is always accepted:

```text
$ gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --frontend react
gobento: cannot create "shop":
  - --frontend: unknown frontend "react"; supported: none, htmx
```

A module no selected component uses:

```text
$ gobento new shop --arch mvc --framework nethttp --db sqlite --data sqlc --pin example.com/x=v1.0.0
gobento: cannot create "shop":
  - module not used by the selection: cannot pin example.com/x, no selected component uses it
```

The same applies to a module whose [trait condition](/docs/concepts/version-rules#trait-conditions)
the selection does not meet, such as GORM's PostgreSQL driver in a SQLite project:

```text
$ gobento new shop --arch mvc --framework nethttp --db sqlite --data gorm --pin gorm.io/driver/postgres=v1.6.3
gobento: cannot create "shop":
  - module not used by the selection: cannot pin gorm.io/driver/postgres, it is only used with sql-dialect postgresql
```

A violated [constraint](/docs/concepts/version-rules#constraint-errors) is
reported as
`incompatible versions: <module> <version> requires go <range>, but go <version> is selected`.

The ranges and versions in these outputs are today's rules. The
[Components reference](/docs/components) always shows the current ones.
