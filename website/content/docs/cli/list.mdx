---
title: gobento list
description: Reference for gobento list, the command that shows the supported components, selections, and versions, as text or JSON.
---

## Synopsis

```text
gobento list [flags]
gobento list components [--kind <kind>] [flags]
gobento list selections [--arch <name>] [--framework <name>] [--db <name>] [--data <name>] [--frontend <name>] [flags]
gobento list versions [flags]
```

`gobento list` shows what your gobento binary supports: the components of
each kind, the selections `gobento new` accepts, and the version rules. It
reads them from the catalog and rules built into the binary, the same ones
`gobento new` uses and the website is built from, so the output always matches
the version you run.

`gobento list` without a subcommand prints all three sections, under the
headings `Components`, `Selections`, and `Versions`. It never asks a question,
writes a file, or uses the network, so it works the same in a terminal, a pipe,
or CI.

## Flags

| Flag           | Applies to   | Description                                                                         |
| -------------- | ------------ | ----------------------------------------------------------------------------------- |
| `--json`       | every form   | Print one JSON document instead of text. See [JSON output](#json-output).           |
| `--kind`       | `components` | List only one kind: `architecture`, `framework`, `database`, `data`, or `frontend`. |
| `--arch`       | `selections` | List only the selections with this architecture.                                    |
| `--framework`  | `selections` | List only the selections with this HTTP framework.                                  |
| `--db`         | `selections` | List only the selections with this database.                                        |
| `--data`       | `selections` | List only the selections with this data-access library.                             |
| `--frontend`   | `selections` | List only the selections with this frontend, or with `none`, those without one.     |
| `-h`, `--help` | every form   | Show the command's help.                                                            |

The selection filters have the same names as the component flags of
[`gobento new`](/docs/cli/new#flags), and they combine: every filter you give
must match.

## Components

`gobento list components` prints each kind with the `gobento new` flag that
selects it and the kind's description, then each component with its name (the
value for the flag), its title, its description, and the
[traits](/docs/concepts/traits) it provides and requires. Traits are sorted by
name; `a|b` means that a component accepts either value. This is the output for
today's databases; gobento's tests check that it matches the CLI exactly:

{/* list-components-database */}

```text
$ gobento list components --kind database
Database (--db)
Where the project stores its data.

  postgres  PostgreSQL
            PostgreSQL through pgx, a pure-Go driver, used with database/sql.
            provides: conn=database/sql, sql-dialect=postgresql, sql-schema=schema.sql
  sqlite    SQLite
            SQLite through modernc.org/sqlite, a pure-Go driver that needs no cgo.
            provides: conn=database/sql, sql-dialect=sqlite, sql-schema=schema.sql
```

An optional kind, such as the frontend, says so after its flag and lists
`none` first: the value that selects no component of the kind, which is also
the default.

{/* list-components-frontend */}

```text
$ gobento list components --kind frontend
Frontend (--frontend, optional)
Web pages served next to the API, which then moves under /api.

  none  No frontend (the default)
  htmx  htmx + templ
        Server-rendered pages written as templ components, made interactive with htmx, and served by the Go binary with no build step.
```

## Selections

`gobento list selections` prints every supported selection, one per row with
one column per kind, followed by their number. A selection without a frontend
shows `none` in the `FRONTEND` column. These are exactly the combinations
`gobento new` accepts; gobento's CI generates and tests every one without a
frontend and a covering set of those with one. With filters, the last line
says how many of all supported selections match:

{/* list-selections-mvc-postgres */}

```text
$ gobento list selections --arch mvc --db postgres --frontend none
ARCHITECTURE  FRAMEWORK  DATABASE  DATA  FRONTEND
mvc           chi        postgres  gorm  none
mvc           chi        postgres  sqlc  none
mvc           gin        postgres  gorm  none
mvc           gin        postgres  sqlc  none
mvc           nethttp    postgres  gorm  none
mvc           nethttp    postgres  sqlc  none

6 of 60 supported selections.
```

Any row is a valid `gobento new` command: for the first one,
`gobento new shop --arch mvc --framework chi --db postgres --data gorm`
(`--frontend none` is the default and can be left out).

## Versions

`gobento list versions` prints the supported Go range and the default Go
version, then every module of the [version rules](/docs/concepts/version-rules),
sorted by path: its role (`library` modules can be chosen with
`gobento new --pin`, `tool` modules are fixed), its range and default, the
components that use it, and the trait values it is limited to (`-` for none).
Constraints between versions follow the table, and then the files components
vendor from an upstream release, such as htmx, whose versions are fixed per
gobento release and cannot be pinned. For example (the values are today's
rules):

```text
$ gobento list versions
Go >=1.26 <1.28 (default 1.27)

MODULE                    ROLE     RANGE              DEFAULT    USED BY            ONLY WHEN
github.com/a-h/templ      library  =v0.3.1100         v0.3.1100  frontend/htmx      -
github.com/gin-gonic/gin  library  >=v1.11.0 <v2.0.0  v1.12.0    framework/gin      -
...
github.com/libtnb/sqlite  library  >=v1.1.0 <v2.0.0   v1.2.2     data/gorm          sql-dialect=sqlite
...
modernc.org/sqlite        library  >=v1.61.0 <v2.0.0  v1.61.1    database/sqlite    -

Constraints:
  github.com/libtnb/sqlite >=v1.2.0 needs gorm.io/gorm >=v1.31.2
  gorm.io/driver/postgres >=v1.6.2 needs gorm.io/gorm >=v1.31.2
  modernc.org/sqlite >=v1.61.0 needs go >=1.26

Vendored assets (fixed per gobento release):

ASSET     VERSION  USED BY        SOURCE
htmx.org  2.0.11   frontend/htmx  https://registry.npmjs.org/htmx.org/-/htmx.org-2.0.11.tgz
```

Read a constraint as: while the module's version is in the first range, the
target (`go` or another module) must be in the second. `github.com/libtnb/sqlite`
is added to a project only when it uses GORM with SQLite.

## JSON output

With `--json`, every form prints one JSON document instead of text, for
scripts and tools. `gobento list --json` prints the catalog document the
website is built from, with these fields:

| Field        | Contents                                                                                                                                                 |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kinds`      | Each kind's `id`, `title`, `description`, and `optional` (whether a selection may leave it out), in canonical order.                                     |
| `components` | Each component's `id` (`<kind>/<name>`), `kind`, `name`, `title`, `description`, `provides` (trait to value), and `requires` (trait to accepted values). |
| `go`         | The Go `range` and `default`.                                                                                                                            |
| `modules`    | Each module's `path`, `components`, `traits` (the trait values it is limited to), `role`, `range`, `default`, and `constraints`.                         |
| `assets`     | Each vendored file's `name`, `components`, `version`, and `source`.                                                                                      |
| `supported`  | Each supported selection, as an object from kind to component name, without an entry for an optional kind it leaves out (no `frontend` means none).      |
| `rules`      | The patterns and messages for the project name and module path.                                                                                          |

Each subcommand prints an object with only the fields it lists, in the same
format: `components` prints `kinds` and `components`, `selections` prints
`supported`, and `versions` prints `go`, `modules`, and `assets`. Filters apply to the
JSON as well. Lists are empty (`[]`) rather than `null`, and objects without
entries are `{}`. Later releases may add fields; renaming or removing one is a breaking change
and is announced in the changelog.

```sh
# The names of the supported databases
gobento list components --kind database --json | jq -r '.components[].name'

# Every supported selection as a gobento new command
gobento list selections --json |
  jq -r '.supported[] | "gobento new shop --arch \(.architecture) --framework \(.framework) --db \(.database) --data \(.data) --frontend \(.frontend // "none")"'

# The default version of a module
gobento list versions --json | jq -r '.modules[] | select(.path == "gorm.io/gorm") | .default'
```

## Exit status

| Status | Meaning                                                                                                  |
| ------ | -------------------------------------------------------------------------------------------------------- |
| `0`    | The list was printed. A filter that matches no selection prints `No supported selection matches.`        |
| `1`    | An unknown subcommand, kind, or component name, or an unexpected argument. Nothing is printed on stdout. |

An unknown name is reported with the names that exist:

```text
$ gobento list selections --db mysql
gobento: --db: unknown database "mysql"; supported: postgres, sqlite
```
