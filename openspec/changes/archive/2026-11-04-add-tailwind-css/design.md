# Design

## Context

See proposal.md for the motivation. The relevant current state:

- `catalog.Kinds()` lists five kinds; `frontend` is the only optional one.
  `Selection` has one field per kind, `Candidates` iterates "no component"
  first for optional kinds, and the CLI, the questions, the listing, the
  catalog export, and the website iterate the kinds. The CLI asks an
  optional kind only when the supported selections that match the earlier
  answers leave more than one option, "None" included.
- Only the base layer declares contribution points (`base.yaml`); `contrib`
  is a function of the base layer's templates. Contributions are rendered
  in kind order, trimmed, and skipped when empty.
- `frontend/htmx` owns the whole `web` slot: `pages.templ`, the shipped
  `pages_templ.go`, `static/styles.css` (plain CSS), and the vendored
  `static/htmx.min.js`, all embedded. `templ-fresh` in gobento's CI checks
  `pages_templ.go` in a reference project.
- The rules file knows Go modules, vendored assets (one file from an
  upstream archive), and tooling versions (images, actions, `go run` tools).
- A Vite change is in flight in parallel. The agreed contract: frontends
  provide the trait `frontend-build` (`go` for htmx, `vite` for Vite), and
  the new kind `css` requires it.

## Goals / Non-Goals

**Goals:**

- `--css tailwind` with htmx: Tailwind styles, regenerated by `make
  generate`, checked by CI, and no Node.js. A project must build with
  plain `go build` and without the Tailwind CLI.
- No per-combination templates: htmx does not name Tailwind, and Tailwind
  does not name htmx.
- A hook that the Vite frontends can adopt without changing `css/tailwind`.

**Non-Goals:**

- Other CSS frameworks (they follow the same pattern), Tailwind plugins, or
  a Tailwind config file (Tailwind v4 is configured in CSS).
- Implementing the Vite side; this change defines and tests the hook.
- Caching the Tailwind CLI in the generated CI workflow.

## Decisions

### D1. An optional kind `css`, offered through the `frontend-build` trait

`catalog.KindCSS` (`css`) joins `Kinds()` after `frontend`, and
`Kind.Optional()` reports it. `Selection.CSS` is nil for none; the flag is
`--css`, the question "CSS framework", with "None (plain CSS)" first.
`css/tailwind` requires `frontend-build: [go, vite]` and provides `css:
tailwind`. Without a frontend no component provides `frontend-build`, so
every candidate with a CSS framework fails its trait check: the only
supported value is none, the interview leaves it alone (one option, and
"none alone is what an omitted optional flag means"), the equivalent command
omits it, and the website disables the choice. No CLI or website code knows
that `css` depends on `frontend`; the dependency is data.

Alternatives considered:

- *A trait or flag of the htmx component* (`--frontend htmx --tailwind`):
  every frontend would need its own option, the Vite frontends would copy
  it, and the configurator would need a new kind of control.
- *Frontend variants* (`htmx-tailwind`): multiplies frontends by CSS
  frameworks, the per-combination templates the composition design avoids.
- *A required `css` kind with a `plain` component*: makes `--css`
  necessary or a `plain` component that ships nothing; "none" is already
  the meaning of an omitted optional kind.
- *An explicit "kind A needs kind B" rule in the catalog*: a second
  mechanism next to traits that the CLI, the configurator, and coverage
  would all have to learn.

### D2. The frontend kind declares contribution points; CSS frameworks contribute

A kind directory may hold `kind.yaml` with `contributions:` in the format of
`base.yaml`; every component of the kind may then include those points with
`contrib "<point>"` in its templates (files and notes). The base layer's
templates name only the base layer's points, and a component's templates
only its kind's. The loader checks that a contribution names a point of the
base layer or of a kind (the error lists them) and that no kind redeclares
a point of the base layer or of another kind. Composition renders a
contribution first and skips it when it is empty, then requires that the
base layer or the kind of a selected component declare its point, and after
rendering fails for any contribution that no template included, naming it,
so a frontend that does not use a point cannot silently drop a CSS
framework's work.

`components/frontend/kind.yaml` declares `stylesheet` ("the complete
stylesheet served as `/static/styles.css`") for `frontend-build: go`, and
the Vite points of D6. htmx's `static/styles.css.tmpl` is
`{{with contrib "stylesheet"}}{{.}}{{else}}<plain CSS>{{end}}`, and its
notes describe the plain CSS only when nothing contributes.

Alternatives considered:

- *Points declared by each frontend in its `component.yaml`*: the Vite
  points would have no declarer until the Vite frontends are merged, so the
  shipped Tailwind contributions to them would be rejected as typos; and
  every Vite frontend would repeat the same declarations. The contract
  between two kinds belongs to the kind.
- *htmx branches on the trait `css: tailwind`*: htmx would name each CSS
  framework, and `pages.templ` and the shipped `pages_templ.go` would get
  one variant per framework inside templ's generated string literals, each
  needing its own freshness check.
- *A new slot for styles, filled by the `css` kind*: an architecture would
  have to know where each frontend keeps its styles (`static/` for htmx,
  `frontend/src/` for Vite), and a slot is a Go package.
- *Letting the `css` kind write into the `web` slot*: breaks "one owner per
  slot".
- *More base layer points*: the base layer owns tooling files, not the
  frontend's files.

### D3. A template that renders to whitespace produces no file

`css/tailwind` ships `tailwind.css` and `internal/tools/tailwindcss/` only
for `frontend-build: go`; for Vite builds the Vite plugin does that work.
Each such template is wrapped in `{{if eq (index .Traits "frontend-build")
"go"}}`, and the composer writes no file for a template whose output is
empty or whitespace only, as it already does for contributions. The
templates of the shipped catalog that render nothing are reviewed by the
goldens (`TestGoldenComponents` composes each component).

Alternatives considered: *a `when:` condition per file in
`component.yaml`* (a second template language for conditions, and the file
list moves away from the files); *two components* (`tailwind` and
`tailwind-vite`), which would show the build system to users who only
choose "Tailwind CSS".

### D4. Semantic markup, Tailwind in `tailwind.css`, shipped pre-built

htmx's markup stays as it is for every CSS choice: elements and the classes
`row`, `empty`, `problem`, and `name`. `tailwind.css` at the project root
is the Tailwind source:

```css
@import "tailwindcss" source(none);
@source "./internal/views/**/*.templ";
@layer components { .row { @apply flex gap-2; } ... }
```

It styles the same markup with `@apply` and Tailwind's theme (colors, dark
mode through `prefers-color-scheme`, focus rings), and scans the web slot's
`.templ` files, so utility classes added to the pages are compiled too.
`css/tailwind` ships the stylesheet the pinned CLI compiles from it with
`--minify` as its `stylesheet` contribution (like `pages_templ.go`, the
shipped output names the version that made it). `source(none)` keeps
Tailwind from scanning the rest of the project, whose README and Go files
would add classes that differ per selection. The only selection-dependent
text in the scanned file is the package name and import paths, which
Tailwind does not extract classes from; the project name moves from
`pages.templ` to a Go constant in `handler.go` (`title`), because a project
named `grid` or `container` would otherwise add a utility. So the shipped
output is the same for every architecture and project name, which the
integration test checks.

Alternatives considered:

- *Utility classes in the shipped markup*: the markup is htmx's and
  shared by every CSS choice (D2).
- *Compile at generation time*: generation would download a 100 MB binary
  and need network access for every `gobento new`, and `--dry-run` would
  differ from the real run.
- *No pre-built output, compile in the Dockerfile and CI*: `go build`
  without the CLI would embed a missing stylesheet.

### D5. The standalone CLI as rules-file data, run by a Go program

Tailwind's standalone CLI is a self-contained binary per platform; there is
no `go run`-able Tailwind. The rules file gets a `binaries` section:

```yaml
binaries:
  tailwindcss:
    components: [css/tailwind]
    version: 4.3.4
    checksums: https://github.com/tailwindlabs/tailwindcss/releases/download/v4.3.4/sha256sums.txt
    platforms:
      linux/amd64: { url: https://github.com/.../v4.3.4/tailwindcss-linux-x64, sha256: 149a8e... }
      ...
```

`compat.ParseRules` checks the version, that each platform key is
`GOOS/GOARCH`, each URL is https and contains the version (so a bump cannot
forget a URL), each checksum is 64 lowercase hex digits, and that the name
is not also a module or asset; `CheckComponents` checks the components.
Binaries are fixed per release (a pin is `ErrNotPinnable`), resolved for
the selected components, and exposed to templates as `.Binaries.<name>`
with `.Version` and `.Platforms` (`.OS`, `.Arch`, `.URL`, `.SHA256`). A
network test fetches `checksums` and compares every platform's SHA-256
with it, so no 100 MB download is needed to verify a bump.

The generated project gets `internal/tools/tailwindcss/main.go`, a
standard-library program with that table: it picks the entry for
`runtime.GOOS/GOARCH`, downloads it once into the user cache directory
(`<cache>/tailwindcss/<version>/`), refuses it unless the SHA-256
matches, and runs it with the given arguments. `TAILWINDCSS=<path>` uses
another binary instead (for example on musl Linux or Windows on ARM, which
the release does not cover). `make generate` and the README run `go run
./internal/tools/tailwindcss --input tailwind.css --output
<web>/static/styles.css --minify`; the CI step runs the same and fails on
a diff. Make stays the only prerequisite besides Go, as for golangci-lint
and sqlc.

Alternatives considered:

- *curl and sha256sum in the Makefile*: differs on macOS (`shasum`) and
  Windows, and fails without make.
- *A third-party Go wrapper module*: an extra dependency of unknown
  maintenance in every project, for 150 lines of standard library code.
- *npm and `@tailwindcss/cli`*: needs Node.js, which htmx projects avoid.
- *Recording binaries as assets*: assets are vendored files with one
  checksum; binaries are downloaded on demand per platform.
- *Caching the CLI in CI with actions/cache*: a second pinned action for a
  ~2 second download.

### D6. The Vite hook

A Vite frontend provides `frontend-build: vite` and includes these points of
`components/frontend/kind.yaml` in its templates; `css/tailwind`
contributes to them when `frontend-build` is `vite`:

| Point | Contribution of `css/tailwind` | Where the frontend inserts it |
|---|---|---|
| `vite-config-imports` | `import tailwindcss from "@tailwindcss/vite";` | top of `vite.config.*` |
| `vite-plugins` | `tailwindcss(),` | the `plugins` array |
| `css-imports` | `@import "tailwindcss";` | top of the app's main stylesheet |
| `npm-dev-dependencies` | `tailwindcss@4.3.4` and `@tailwindcss/vite@4.3.4`, one per line | `npm install --save-dev` after scaffolding |

The npm versions are the binary's version: Tailwind releases the CLI and
the npm packages together. A compose test builds a catalog from the shipped
components plus a fixture Vite frontend (`internal/compose/testdata/`) and
checks each insertion and that no `tailwind.css`, helper program, or
Tailwind `make generate` line appears. Until a Vite frontend includes the
points, its Tailwind selections fail to compose (a contribution that no
template includes) and are therefore unsupported, never broken.

### D7. Coverage, CI, and the website

`Coverage` already covers pairs across every optional kind, so the pairwise
set grows to include `css` pairs; the integration test runs the Tailwind
command in each covered Tailwind project and fails if a planned file
changes, and one more Tailwind project, named `container`, checks D4's
independence of the project name. gobento's `templ-fresh` job becomes a
matrix over `--css none` and `--css tailwind`, and the Tailwind leg also
runs the Tailwind command, so both shipped outputs are checked in one place.
The website reads kinds, optional flags, and binaries from the export; the
configurator's tray gets a sixth compartment, and the packing stage derives
its layout from the number of kinds instead of assuming five.

## Risks / Trade-offs

- [The shipped stylesheet drifts after a Tailwind bump or an htmx markup
  change] → `templ-fresh` (Tailwind leg) and the integration test fail;
  the contributor guide has the regeneration steps.
- [A 100 MB download on the first `make generate` and in each CI run] →
  Cached per user and version; CI downloads in seconds; building never
  needs it.
- [The release has no binary for a platform (musl, Windows on ARM)] → The
  program names the supported platforms and the `TAILWINDCSS` override.
- [Users expect utility classes in the starter page] → The notes explain
  the semantic classes and that utilities in `.templ` files are compiled.
- [Empty-template skipping hides a template that renders empty by mistake]
  → Goldens list every planned path, so a missing file shows in review.
- [A kind-level point that a frontend does not include] → Composition fails
  for any contribution no template included, so the selection is
  unsupported and `TestShippedCatalogSupported` names it.

## Migration Plan

Additive: without `--css` nothing changes except `pages.templ`, which gets
the title from a Go constant (visible in the htmx goldens). The Vite branch
merges by adding `frontend-build: vite` to its components and including the
points of D6 in their templates; both branches add the same
`frontend-build: go` line to htmx.
